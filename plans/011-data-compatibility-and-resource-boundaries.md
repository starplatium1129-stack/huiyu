## 011-B1：未知新版拒写与显式迁移

### 定位与边界

主要文件：`src/utils/chatStorageCore.ts`、`src/composables/chat/useChatStorage.ts`。相邻读写者包括 `chatArchive.ts`、`chatMemory.ts`、`retiredCompanionChat.ts`、`backupCore.ts`、`backupSettings.ts`。复用现有 `scripts/tests/test-chat-storage.ts`、`useChatStorage-credentials.spec.ts`、备份与浏览器存储回归；先盘点已有版本机制，避免复制已存在的 decoder。

### 实施步骤

1. 用生产解析函数建立 version 缺省、合法旧版、当前版、未来版、非法版本五组中性夹具。记录原始字符串和未知字段，验证当前未来版降级及自动回写路径；不能只断言一个常量存在。
2. 在任何归档溢出迁移、退休角色迁移、规范化回写、凭据旧字段清理之前识别输入版本。将结果分为可读可写、可迁移、未知新版、损坏；未来版本和非法格式不得静默当成当前版本。
3. 对支持的旧版本定义明确迁移路径，合法既有记录保持兼容。当前版本继续保留已有字段白名单和凭据脱敏；不为保留未来字段而放宽当前格式安全规则。
4. 未知新版原件保留在原位置，不打印内容，不自动复制到可能进入 Git/备份的目录。界面提示当前版本无法安全修改，禁止会写回该记录的发送、自动保存、清空及相关迁移；不要用空记录替代加载失败。读取其他不相干设置不必全部禁用。
5. 在写入前重读并校验当前持久化版本，防止“先加载旧版，另一窗口写入新版，再保存旧快照”的时序。所有写入口共用守卫，不能仅保护首次 load。
6. 将同样的版本矩阵用于归档/记忆/恢复涉及的格式：优先保护实际存在的版本字段；无版本格式先写清兼容契约，不能凭空把缺字段视为未来版本。
7. 在隔离浏览器中验证未知新版→打开→切角色/设置→重载后原始数据字节不变，支持旧版迁移后能正常发送和保存；两页交错后旧页明确停止写入。

### 验收与回退

- 未来版哨兵字段、消息、原始版本均不丢；保护不能只保留内容却改写版本。
- 已支持旧版和当前版行为通过；当前 API 凭据迁移、清除、脱敏不回归。
- 写入被拒绝时有明确状态，不能提示保存成功；归档/退休迁移没有先于拒写偷偷改变其他键。
- 回退时继续保留未来版拒写与原件，不以恢复旧读写器来“解决”未知数据；迁移路径必须可幂等重试。

## 011-B2：删除承诺、实际集合与失败语义一致

### 定位与产品决定

主要文件：`useCharacterRoomSession.ts` 的 `clearAllMemory`、`useChatStorage.ts`、`chatArchive.ts`、`chatMemory.ts`、`retiredCompanionChat.ts`、`storageKeys.ts`、`settingsRepository.ts` 和备份导出。当前“全部本地聊天数据已重置”与实际清理范围不一致。

本批将操作准确定位为“清空本机聊天内容与个人档案”：覆盖所有当前/退休角色的对话、历史归档、事实记忆、逐角色/旧格式草稿、个人称呼与备注，以及本会话相关语音缓存。保留 API 连接/凭据、外观、音量、模型资源和行为偏好；按钮、确认与成功文案明确这一边界，不再声称全部配置也被重置。已经导出的旧文件和第三方服务记录无法被本地清除，不承诺删除它们。若现有 UI 有更明确的已接受范围，按其核对后记录等价决定，不能静默增加删除对象。

### 实施步骤

1. 建立一张存储对象表：来源、键/前缀、当前/退休角色、内存副本、写入者、备份导出关系、清除/保留决定。不要使用 `localStorage.clear()` 或按模糊前缀删除整个库。
2. 以不同中性哨兵写入对话、归档、记忆、草稿、退休数据、个人档案及应该保留的配置。覆盖“仅有其中一种数据”的状态，修正 `hasMemory` 提前返回遗漏。
3. 将清除过程从 View/session 的散落写入整理成有返回结果的清除用例，沿用已有仓储。停止对应在途聊天/语音，更新内存状态与持久化状态；清除成功后旧回调不得重新发布。
4. 复用既有修订/墓碑协议覆盖新增清除集合。两个窗口中，一个清除、另一个迟到保存或输入草稿时，已清除内容不得复活。新输入与旧数据区分，不能永久禁止用户继续聊天。
5. 对单个设置删除、归档保存、记忆保存和存储不可写分别注入失败。汇总未完成项，提供安全重试；只有约定集合实际清理成功才显示完成。不得因部分失败回滚并复活已经删除的私密内容。
6. 验证重载、重新注册退休角色和新备份导出不再包含被清除的哨兵；应保留的设置、凭据和作品库逐项不变。
7. 文案/交互改动完成后，做深浅主题、键盘确认/取消/失败重试和焦点恢复；提供两主题截图与必要实际对比度证据。

完成条件：存储对象表与界面承诺一致；“仅草稿/个人档案/退休存档”都可清除；失败如实反馈；双窗口不复活；当前生成结果与作品库不受影响。回退只撤回代码/交互，不恢复用户已经主动删除的内容，不额外保留隐藏的明文副本。

## 011-B3：流式响应资源预算与结束协议

### 定位与边界

主要文件：`routes/chat.ts` 的兼容 SSE 消费、`services/ollama-service.ts` 的 NDJSON、`services/http-client.ts`、聊天事件/工具调用消费者及相关测试。已有请求字节限制、socket idle timeout、队列和取消继续保留。新的总时限不能取代 idle timeout，也不能影响合法长任务的其他调用方。

### 实施步骤

1. 建立只监听临时回环端口的假上游：超长无换行数据、持续小滴流、超长工具参数/推理、畸形字段、UTF-8 跨片、EOF 缺终止、重复终止、客户端取消。用很小的可注入预算快速复现，不向本机模型发请求。
2. 清点上游协议的合法结束条件和现有输入验证上限。设计共享但协议无关的预算状态：累计原始字节、未完成帧字节、累计推理、工具数量及参数字节、绝对 deadline；SSE/NDJSON 各自仍负责语义解析。
3. 初始候选值为单帧 1 MiB、总响应 16 MiB、总时长 10 分钟；推理/工具参数上限优先复用后续请求现有校验常量，禁止接收一个必然无法继续对话的结果。执行者核对当前受支持模型输出约定后固定默认值并写明依据；测试注入缩小预算，不等待十分钟或分配巨量数据。
4. 在字符串拼接/JSON 解析前检查字节预算，避免先完整累积才拒绝。用增量 UTF-8 decoder，覆盖 frame/comment/空行及非 streaming fallback，错误响应也受已有上限约束。
5. 绝对 deadline 从实际上游请求开始，队列等待按已有队列策略单列；超限/取消后中断本请求、释放 socket/队列槽/定时器。客户端断线同样终止上游。不得按进程名杀模型或影响其他用户请求。
6. Ollama 缺 `done` 不再自动宣布成功；兼容 SSE 按供应商协议区分有效 finish_reason、合法非流式成功和意外 EOF，不机械要求所有供应商只能用一种结束标记。没有完整终态时保留部分文本并明确失败/中断，不执行半截工具调用。
7. 整合前端错误状态：可继续提问/重试但不自动重发可能有副作用的工具；错误码和诊断只记录数量、阶段、时间与匿名任务 ID，不含完整文本、密钥或工具参数。

验收：预算边界内成功、刚超出即拒绝；滴流仍会在总期限终止；UTF-8 不损坏；终态只发一次；缺终态/畸形工具不算成功；并发中的其他请求正常；取消后没有遗留 timer/listener/队列占用。回退按协议开关分批处理，不能移除资源硬边界或重新把意外 EOF 视为成功。

## 011-B5：素材生命周期、配额与解码预算

### 定位与先行核验

入口为 `routes/video.ts`、`routes/video/media.ts`，相邻 `routes/anima.ts`、`src/utils/imageThumb.ts`。先盘点 reference/input 的持有者、项目/批次引用、写入/取消/删除/重启路径，以及现有资源清理工具。已有 28 MiB JSON/20 MiB 单文件等限制按当前源码核对，不把它们误报为不存在。

### 实施步骤

1. 在唯一临时素材根通过真实路由连续上传同一中性图片，记录文件数、字节、响应标识、任务/参考引用；验证目前是否有别处去重或配额，不能只看单一路由下结论。
2. 为可共享参考按实际内容哈希去重；上传原始字节的哈希相同才视为同一内容，不只比较文件名。保留访问/所属边界，不能让一个身份通过去重响应探测其他私有资源。
3. 定义累计字节、文件数和正在写入预约的预算。复用现有配置入口，不新增隐式无限模式；默认限额先根据现有合法样本/使用说明确定并记录。测试注入小容量，覆盖两个并发上传争最后一份容量、失败释放预约、重复上传不重复计费和进程重启重新核算。
4. 写入使用本次拥有的临时文件和原子发布。跨进程可能共用根时使用已有租约/锁，而不是仅靠内存计数。显式超额错误携带安全的容量摘要，不泄露真实本机路径。
5. 独立检查解码维度：文件类型/魔数、宽高、总像素、帧数和并行解码数。复用现有图片库，不因扩展名/Content-Type 合法就认为安全；在受限解码器/子进程中测试小字节大尺寸声明、截断、损坏和动画多帧。UI 解码也需入口限制，不能先铺满 Canvas 才报错。
6. 制定安全回收规则：任务临时 input 与持久 reference 分开；共享参考仍被项目、任务或待保存会话引用时不删除。先做扫描/预览，再提供明确的未引用回收；未知归属保留，不自动清用户旧目录。到达配额时宁可拒绝新上传并给管理入口，不能直接删除最旧文件腾空间。
7. 中性 HTTP 与文件夹具验证取消、写盘失败、崩溃残留、重启、同文件并发、引用删除。真实磁盘满/超大用户素材/设备峰值继续单列主力机，不在办公机制造系统资源耗尽。

完成条件：去重与容量账目可解释；并发不能超卖；失败无半成品；用户可识别配额错误；受引用资产不误删；解码输入在消耗巨量资源前受限。若调整默认上限，合法现有输入的兼容性必须有测试。回退只撤回新增上传策略或关闭新上传，已存在参考与用户原件保持可读；不迁移或清空素材库。

## 011-B6：源码、构建与发行产物的强制绑定

### 定位与原则

入口：`scripts/maintenance/release-desktop-update.ts`、`build-modern-installer.ts`、构建/桌面暂存入口及现有 capture/audit delivery 模块。复用现有回执和依赖哈希，不另建一套平行发行账本。本批测试完全使用临时根、假 exe/签名调用和注入的 Git/GitHub 命令适配器，不能调用真实 publish、上传 Release 或读取生产签名私钥。

### 实施步骤

1. 建立反例：同版本号在提交 A 生成产物，源码变到提交 B 后工作树干净，模拟 `--skip-build --publish`；核对当前检查是否拒绝。如果已有完整绑定，证明实际执行到了该守卫并保留回归即可。
2. 明确发行输入集合：受影响源码、版本文件、npm/Cargo 锁、前端 manifest/首页、原生程序、随包 Node/网关和安装 wrapper/payload。对每个身份区分源码内容哈希、构建产物哈希和最终提交，不能用版本号相同代替身份相同。
3. 在受控构建前捕获输入身份，完成后绑定实际产物；再签名/发布时核对双方。构建发生在版本修改未提交期间的正常流程，应允许后续提交相同内容并绑定最终 SHA，不误要求不可能存在的循环提交哈希。
4. 缺回执、陈旧源码、锁文件变化、前端/原生混包、产物被改写均在任何签名或远端写入前拒绝。`--bundle-only`、`--manual`、`--complete-manual` 同样定义绑定要求，不能让替代模式绕过。
5. 完整沿用当前原私钥、公钥和手动版规则。补签只针对原发行源码/精确 payload，不生成替代密钥、不把相同版本的重建包当成原资产。错误信息给出重建或选择匹配回执的步骤，不打印密钥/签名秘密。
6. 让测试证明：正确绑定成功；A→B 同版本旧包失败；篡改/缺文件/空回执失败；仅文档变化是否失效按已声明输入域解释；远端上传失败仍保持 draft，不提前晋升发布。
7. 更新正式发布工作流与部署文档的必要说明；不实际发布或安装。新增维护入口才登记 `scripts/workflow.ts` 和 `docs/workflow.md`，不要为普通内部 helper 增加不必要命令。

验收：预检失败时签名/上传调用次数为 0，最终包的每层身份都能回溯到受控构建；正常手动与签名流程不互相冒算。回退必须保留预检，不能恢复以同版本号放行陈旧包；不修改已公开标签/Release 资产。
