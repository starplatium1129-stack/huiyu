## 1. 目标与范围

让绘遇桌宠从“围绕两个内置角色组织的功能入口”，逐步成为**角色始终在场、交互不打扰、聊天可自然展开、添加模型以配置为主的陪伴系统**。

主线是三件事：

- **陪伴式界面**：角色画面优先，安静陪伴、轻量对话、完整聊天各有合适的信息量；工具与诊断按需展开。
- **可扩展的陪伴角色注册**：角色身份、模型外观、声音与记忆分别管理；新增陪伴角色不要求复制页面或修改核心角色分支。
- **通用模型适配**：资产检查、运行时参数探测、语义映射、能力报告与可视化校准组成完整流程；保留精细适配和安全降级。

### 1.1 必须保留的边界

保留 Vue／TypeScript、Tauri 与现有 Native／Browser Live2D 路线，不为本计划整体更换技术栈。复用已有后端抽象、陪伴状态、语音生命周期及表现配置，不另造第二套互相竞争的状态机。

遵循 [DESIGN.md](../DESIGN.md) 与 [协作指南](../AGENTS.md)：保留绘遇的日系画室与角色品牌语言，支持深浅主题；图标继续使用手绘线条机制；静态立绘不做假呼吸；高频界面动画以 `transform`／`opacity` 为主。苹果式流畅是交互目标，不意味着复制苹果外观或保证固定帧率。

保留现有本机／远程权限、内容分级、素材授权、工作区边界和用户数据。未知角色不能静默落到宁宁；导入一个模型不能自动赋予角色所有工具权限，也不能自动获得角色人格或音色授权。

### 1.2 本计划不承诺什么

- 不承诺所有 Live2D 模型零配置、固定“80–90% 适配率”或“五分钟完成”。这些只能由定义清楚的样本集与实际操作记录得出。
- 不把文件存在、参数名称匹配、SDK 加载成功、视觉正确四种状态混为一谈。
- 不承诺通用层零开销或天然更丝滑；需要同设备、同模型、同画质比较帧时间和资源占用。
- 不把模型缺失的绑定、动作或表情凭空补出来；没有可靠能力时正常降级。
- 暂不做多人同时常驻、多角色群聊、角色商店、云端角色分发、摄像头情绪推断、微信接入或模型自动制作流水线。

## 3. 陪伴式 UI 与聊天窗口方案

### 3.1 一段会话，三种展示形态

| 展示形态 | 建议界面 | 行为约束 |
| --- | --- | --- |
| 安静陪伴 Ambient | 角色为主；非必要工具栏、历史记录与输入框可收起 | 不主动抢焦点；托盘、快捷键和可访问入口能恢复交互；录音／隐私状态不能被隐藏 |
| 轻量对话 Chat Dock | 角色附近的紧凑聊天面板，近期对话与简洁输入区 | 复用现有独立聊天窗；支持贴靠与解除贴靠；关闭面板不删除记录或中断用户未要求停止的任务 |
| 完整聊天 Expanded | 在较大阅读面板中查看历史、图片、语音、记忆与任务详情 | 延续同一会话与草稿；不重新加载同一个角色、不重复发送或播报 |

这三种形态不等于新增三个原生窗口。C0 先核对现有 Companion、聊天窗与 Atelier 的分工；优先复用现有窗口和路由，只在测量证明必要时另立窗口方案。浏览器端可以使用同页面板，保持交互语义而非强求窗口实现一致。

### 3.2 角色画面

角色不再随聊天记录增长而被不断压缩。气泡只承载当下的一句或一小段发言，历史进入聊天面板。气泡位置以 Profile 中的头部／肩部锚点和安全区域为依据，允许人工调整；缺少锚点时采用可编辑的保守位置，不声称自动识别了脸部。

贴靠规则按屏幕可用区域选择左右侧并防止来回跳动；拖动、DPI 切换、多屏、任务栏与窗口缩放时，角色、气泡、输入区域均应可见。角色点击区与拖拽区分开，操作聊天面板不触发摸头等互动。透明区穿透由壳层验证，不能只依赖 CSS。

短提示可以延时收起，但停留、聚焦、选中文字、屏幕阅读器阅读期间不自动消失。任务失败、权限请求和用户尚未处理的关键确认不得按普通问候自动淡出。

### 3.3 聊天阅读与操作

聊天头部突出角色名称和当前交流状态；切角、设置、历史等采用渐进展开。保持绘遇现有材质与角色强调色，不用大面积高透明文字或连续扫光制造“陪伴感”。

消息样式区分用户、角色、系统与任务结果。长回复自然分段，提供重播、复制与必要的消息操作；角色台词不应长期夹着工具函数名和性能数字。任务说明可以先用简短自然语言，但真实状态、失败原因和权限风险必须清晰可查。

输入区保留文本、语音、发送与停止；支持中文输入法合成期间不误发送、多行输入、按角色保存草稿、失败后保留内容与可控重试。停止按钮始终针对当前轮次；语音失败可继续文字交流。

新消息到达仅在用户接近底部时自动滚动。用户正在看旧消息时保留阅读位置，提供“回到最新”入口。完整文本无需等待配音完成才可读，不人为插入长延迟；可选当前朗读句高亮，历史展开不触发重播。

### 3.4 陪伴节奏与无障碍

使用真实 listening／thinking／speaking／working 状态驱动反馈，避免多处重复“正在回复”。主动问候遵守现有勿扰、安静时段和输入／播放互斥；没有回应时不升级催促，不靠好感度惩罚制造使用压力。

展开收起应连续且可打断；快速重复操作不能留下透明遮挡层。保留键盘导航、焦点返回、Esc 的局部关闭语义、减少动态效果选项与触控可达性。深浅主题、图片背景叠字、错误态、窄窗口都要验收。

## 4. 角色与模型的分层

建议用下面四个概念替代“一个角色目录包办一切”：

| 概念 | 保存内容 | 关键边界 |
| --- | --- | --- |
| Character Definition | 稳定角色 ID、显示名称、人格配置引用、默认外观／语音引用 | 不将所有绘图角色自动变成可聊天角色；保留宁宁／夏目的主角定位 |
| Avatar Definition | 模型资产引用、模型版本／指纹、预览图、授权元数据 | 同一角色可有多个外观；换外观不等于换人格或清除记忆 |
| Live2D Adapter Profile | 语义映射、校准、动作规则、能力声明、布局锚点 | 每个模型版本独立；两个不同模型不能因为角色同名就共用参数索引 |
| User State | 会话、记忆、好感度、用户选定服装、草稿与位置偏好 | 与可分发配置和素材分离；删除外观默认不删除相处数据 |

新增陪伴角色通过注册表与校验入口完成；代码使用经注册表验证的角色 ID，而不是把所有类型直接放宽成任意字符串。旧 `nene`／`natsume` 的 ID 与存储映射保留，迁移要求可重入、失败不破坏旧数据。

未知／已移除角色显示可恢复提示，禁止静默借用其他角色的音色、人格或记忆。新角色缺少 Live2D 时可使用静态立绘，缺少合法音色时保留文字模式；不会因为某项资产未准备好而阻断其他独立功能。

## 5. Live2D 通用适配器

### 5.1 分层与复用关系

```text
Companion UI / 会话与真实任务事件
                 ↓
统一表现意图（聆听、回应、凝视、口型、互动）
                 ↓
现有表现运行时 + 参数／动作调度
                 ↓
版本化 Adapter Profile + 模型能力解析
                 ↓
现有 Browser Backend / Native Backend
                 ↓
当前项目兼容的 Cubism 运行时与模型资源
```

业务层表达“轻微开心”“口型电平”“摸头回应”，不引用模型专属 `Param*` 或动作文件名。参数 ID 保留在 Profile、模型检查器与底层适配器中。底层仍允许读取已验证的配置；“不侵入渲染器”不是禁止渲染端接收模型参数映射。

语义不是每个模型都必须具备。情绪、身体动作、口型、视线、服装状态与一次性互动分别建模，避免把一个 `happy` 同时强制解释为表情文件和全身动作。

### 5.2 导入检查器：文件检查与运行时探测分开

**第一阶段：静态资产检查。** 以 `.model3.json` 为入口核对其引用的 `.moc3`、纹理、动作、表情及可选 physics／pose／userdata。读取可选 `.cdi3.json` 的参数和部件显示名称；整理 `EyeBlink`／`LipSync` 组、动作组、命中区域与缺失文件。官方格式说明见 [JSON 文件说明](https://docs.live2d.com/en/cubism-sdk-manual/json-unity/) 和 [补充显示信息](https://docs.live2d.com/en/cubism-sdk-manual/cdi3json/)。

**第二阶段：兼容运行时探测。** 在资源上限内加载模型，通过项目所用 SDK／后端实际提供的接口读取参数 ID、类型、最小值、最大值、默认值，以及可用动作、部件与命中区域。不能把读取 `.model3.json` 说成已经获得完整参数表。后端暂不支持枚举时明确标为未探测，需要补接口，而不是猜一个结果。

**第三阶段：候选与校准。** 官方 [标准参数表](https://docs.live2d.com/en/cubism-editor-manual/standard-parameter-list/) 是候选识别依据，不是每个模型必须满足的承诺；`LipSync`／`EyeBlink` 声明也要与真实参数集合交叉验证，参见 [口型同步说明](https://docs.live2d.com/en/cubism-sdk-manual/lipsync/)。

候选优先级建议为：用户已确认且仍匹配模型指纹的配置 → 对应版本的内置已验证 Profile → 经运行时核实的模型声明 → 标准参数候选 → 名称启发式候选。未知参数、含糊动作名不自动激活；用户确认覆盖自动建议，但无效范围和不存在的 ID 仍必须拒绝。

识别 `ParamAngleX` 只能说明可能存在头部旋转控制，不能宣称已经具备摄像头人脸追踪。发现 `smile` 文件也不能单凭名字证明其视觉含义为开心。

### 5.3 Profile 的最小契约

以下字段是待 C0/C3 定稿的设计，不是仓库已存在的 API 或可直接运行的配置文件。

| 字段组 | 至少需要包含 |
| --- | --- |
| 身份与兼容 | schemaVersion、profileId、profileVersion、avatarId、模型及依赖指纹、后端／SDK 兼容声明 |
| 参数绑定 | 语义通道、一个或多个目标 ID、实际范围、校准闭合／张开或负向／中性／正向端点、曲线与限幅 |
| 运行规则 | 绝对／叠加／乘法或作者动作优先策略、权重、平滑、释放时机、冲突通道 |
| 表情与动作 | 经确认的表情 ID、动作组与索引、可选变体、优先级、重复限制、结束／中断处理 |
| 互动与持久外观 | 命中区映射、动作控制参数集合、持久服装状态、临时叠层与复位策略 |
| 舞台布局 | 缩放偏移、可编辑发言锚点、安全区域、不同展示形态的构图建议 |
| 来源与验证 | 映射依据、候选／人工确认状态、验证模型指纹、验证后端、待验原因与授权说明引用 |

口型归一化输入可以采用 `v = closed + level × (open - closed)`，再按实际范围限幅；例如方向反转不应靠全局“所有口型都是 0→1”处理。眼睑也需要明确“睁开”和“闭合”的校准值。参数类型／语义不清楚时不参与连续插值。

`neutral` 表示释放本轮临时表现，恢复当前服装和作者基线，不是所有参数写零或所有表情清空。用户选择的持久外观与瞬时情绪必须分开。

### 5.4 能力报告与降级

报告同时展示三层：**后端支持什么、该模型发现什么、在该模型与后端组合上验证过什么**。

每项能力分别标注 `detected`（发现候选）、`needs-confirmation`（待校准）、`verified`（有对应验证）、`unsupported`（不支持）或 `invalid`（配置无效），并附原因。参数检查通过不自动升级成视觉已验证；表情未知不等于没有表情。

默认展示各状态的数量和缺项，不展示一个没有明确分母的“自动适配率”。确需统计时，区分候选识别率、用户确认率、动作正确率和实际人工配置成本，并绑定模型样本及版本。

降级遵循已验证能力：缺少思考动作可保留待机与文字状态；缺少可靠口型保持语音播放但不伪造嘴部变化；缺少表情时保留文本语气和已验证的轻量动作。没有运动能力的静态立绘保持静止。

### 5.5 动作仲裁、复位与会话隔离

按参数通道处理作者 motion、表情、眨眼、口型、凝视和物理计算的覆盖关系。不能通过“最后全量写一遍通用参数”破坏作者动作，也不能在两个引擎中分别执行同一次表情。

可分析 motion 曲线生成受控参数集合与冲突候选，但“曲线差集”不足以自动决定全部复位策略。换装可能应保留，临时叠层可能应恢复；复位值与策略必须允许 Profile 声明并经过预览验证。

动作自然结束、中断、停止、切角、换模型与加载失败都要释放临时状态。优先复用可靠的结束事件，必要时设置有界超时作为清理兜底，不依赖角色专属写死时长作为唯一依据。

意图与回调携带会话／模型实例标识和轮次版本。旧模型的异步 ready、TTS、动作回调不得作用于新模型；快速切换失败应可退回上一个可用外观。

### 5.6 热路径与资源

检查、候选识别、Profile 校验在导入／加载时进行；按模型实例编译并缓存参数句柄或索引。跨模型禁止复用索引，模型／Profile／兼容版本变化触发失效。官方 [参数操作说明](https://docs.live2d.com/en/cubism-sdk-manual/parameters/) 提供 ID 句柄与索引操作的背景。

原生逐帧计算留在渲染端，上层传递有界意图及必要的节流电平，不新增逐帧完整 JSON 解析、磁盘读写或海量跨窗口参数 IPC。保留现有帧率、隐藏／恢复与省电策略，在 C0 基线基础上检查回归，不以目标 FPS 代替真实帧时间。

## 6. 可视化配置工作室与安全导入

推荐入口为“陪伴角色管理 → 外观与 Live2D → 导入／配置”。左侧是模型预览，右侧按“基础、口型与眨眼、表情、动作、互动、布局、诊断”渐进展开；高级参数默认收起。

建议流程：**选择本地模型文件夹 → 检查兼容性与引用 → 生成候选 → 预览校准 → 测试组合行为 → 保存 Profile → 绑定角色**。首版优先支持文件夹；ZIP 在路径与解压上限验证完成后单独启用。选择入口文件时需保留关联目录，不能只上传一个孤立 JSON 就宣称导入完整模型。

预览支持逐项口型／眨眼／凝视测试、表情和动作回放、结束后恢复、当前值与范围显示、停止、一键恢复到安全基线及撤销未保存修改。提供模拟音频电平，不要求启用麦克风或云服务即可做基本校准。高风险参数不进行无差别自动全范围扫描。

“保存”先写草稿并验证，再原子切换有效版本；坏配置不覆盖最后可用版本。保留用户覆盖与内置 Profile 的区别、模型变更提示、导出不含隐私的配置，以及按指定版本恢复。预览与正式陪伴实例隔离，避免测试动作操纵桌面上的另一角色。

### 安全与隐私门槛

- 引用必须解析并限制在用户选定的合法资源根内，覆盖 `..`、绝对路径、符号链接／junction、编码路径与大小写冲突；默认不取远程引用，不执行模型附带脚本。
- 限制文件数、单文件和总资源大小、纹理尺寸、解析深度与加载耗时；ZIP 还需防目录穿越和异常解压体积。加载 `.moc3` 时使用当前 SDK 可用的一致性校验并处理拒绝结果，见 [模型完整性校验](https://docs.live2d.com/en/cubism-sdk-manual/moc3-consistency/)。
- 错误报告不暴露完整个人目录、密钥或对话；Profile 导出不带聊天、好感度、登录状态或供应商凭据。自动识别默认本地完成；未来如增加视觉 AI 建议，另行明确上传、费用与授权，不作首版依赖。
- 导入前记录来源及许可说明；使用权、修改权、演示权和再分发权分别确认。本次不判断或扩大任何现有模型的授权。

## 10. 下一轮讨论：Live2D 模型从哪里来，还是自己做

**本节只保存决策议题，不选平台、供应商、模型或预算，不启动资源获取。** 通用适配器先定义接口并用现有可用资源／隔离夹具推进，避免实现绑定到尚未选择的模型。

待比较四条路线：使用许可合适的现成模型、购买成品、委托原画／拆层／绑定制作、自行设计制作；也可评估“先现成模型验证适配，后制作绘遇专属形象”的组合路线。当前没有默认推荐或已批准方案。

下一轮需要明确：

- 希望增加哪些角色，已有角色外观扩展还是原创绘遇形象；只自己使用、给朋友分享，还是需要公开演示／随软件分发。
- 能投入的预算、时间与绘画／拆层／绑定经验；原创程度、动作丰富度、半身／全身、表情与换装需求。
- 是否交付可运行资源、可修改源工程及维护说明；各项使用、修改、展示、分发许可是否覆盖预期用途。
- 浏览器／Native 的目标兼容性，纹理与资源限制，参数规范、口型／眨眼声明、动作结束与复位约定是否能交付测试。
- 音色另行准备与授权；拥有 Live2D 模型不等于拥有配套声音。

模型来源决定后，再锁定真实验收样本和资源交付清单；参数规范与 Adapter Profile 可以作为委托／自制的交付要求，但不能替代模型实际绑定和视觉验收。
