## 目标与边界

让新增、修改和退役人物／服装／场景时，能明确找到源数据、预览影响范围、选择必要校验并追溯交付证据。保留现有技术栈和工作流入口，不默认建设新 CMS，不因条目增多就把静态内容迁入数据库。

与 [005 架构计划](005-desktop-architecture-consolidation.md) 区分：005 负责桌面布局、状态接口、用户作品持久化与任务恢复评估；本计划负责工程执行流程以及项目自带内容目录的治理。两者复用基础能力，不建立重复的任务或存储系统。

机器分工沿用用户确认：办公机实现、隔离数据／模拟上游测试；主力机真实模型、GPU、桌面设备验收。主力环境为 4K / Windows 150% 缩放。性能改动先测实际瓶颈。

## D5：场景新增与稳定分片

本项针对开发侧维护项目自带场景库。当前安装模式拒绝 `/api/maintenance/scenes` 写入；用户在安装版自建场景属于另一项产品能力，应接用户数据仓储，不能通过解除项目源数据维护限制实现。

本轮只读发现：

- 通用场景按角色／系列分组，每批默认 50 条；维护源与浏览器读取分片已分离，应保留这个基础。
- `useSceneEditorModal` 新增和复制时在前端按当前列表最大 ID 加一；保存接口只接受三位数字 `scNNN`，场景数组上限 1000，蓝图数组上限 2000。扩大容量前需同时核对所有调用者和规则，不直接改变既有 ID。
- 保存接口接收完整场景集；未携带读取基线版本的旧快照需要防覆盖。现有备份与失败恢复机制要保留，但它们不替代版本冲突检测。
- `writeSceneShards` 会按 ID 排序重切整个分组；中间插入／退役可能让后续批次条目移动。`targetFile` 以分类文字是否包含 After_Story 判断归属，应避免展示分类改名意外改变物理分组。
- 分批发现逻辑从 `.1.json` 连续读取，遇到缺号即停止；应检查清单完整性与孤立后续分片，防止把损坏目录视为完整数据。

建议按以下顺序完善：

1. 统一由写入侧分配或确认稳定 ID，检查已存在和已退役 ID，不复用旧身份；并发创建在同一受控写入事务／锁内处理。兼容现有 scNNN，另设计越过 sc999 的格式及所有消费者迁移。
2. 单条新增／修改提交明确的变更集与预期版本。旧版本冲突返回可解释差异；全量导入保留为单独操作，不能与普通保存混为一谈。
3. 显式定义维护分组与场景实体关系，将文件批次作为存储细节。新增条目写入所属分组的稳定目标，仅必要时新开批次；日常新增不自动重新平衡所有文件，重分片另走显式维护流程。
4. manifest 明确可验证的分片集合与顺序，检查缺号、孤立分片、重复 ID、路径和归属冲突；文件写入原子性之外，还需验证多文件更新中断和恢复。
5. 新增前显示所属角色／服装／分组、结构校验和关联影响；创作内容逐条编写。结构通过只表示可继续审核，真实编译／出图和定稿保护仍遵循项目约束。

验收：以临时内容副本覆盖两个旧版本同时创建／保存、退役最高 ID 后再新增、达到批次边界、分片缺号、容量边界及写入中断。正常新增只改变必要源文件与生成产物，既有 ID、顺序契约、深链和受保护内容不变；未审核新内容不得混入已通过的样张状态。

不默认改成一个场景一个文件，不迁移静态内容数据库，不更改现有数据或打开安装版源数据写入口。新 CLI 命令或 API 在实现时按现有工作流和工程契约登记。

## R1：安装包与图片资源分层分发

用户关切：不打包角色图片会导致初次进入空白，全量打包又会随人物和场景增长不断扩大安装包。目标是离线首次进入有完整的基础展示，高清资源按需补充，程序更新不重复携带全部图片。

本轮文件体积盘点：`assets/characters/thumbs` 160 个文件约 2.69 MiB；`assets/characters` 其他文件 174 个约 258.04 MiB；`assets/live2d` 约 66.90 MiB。这里是本机源文件大小，不是压缩安装包大小，也不包括外部参考库。发布前重新统计，不能直接作为下载体积承诺。

现状：桌面暂存复制 assets，已排除 `character-references`；角色缩略图与部分错误占位已有实现，但高清图按需下载、完整离线回退和资源包管理仍需设计。不能只从打包列表删除图片就宣布完成。

建议分层：

| 层级 | 随程序提供的内容／独立内容 | 用途 |
| --- | --- | --- |
| 必需基础资源 | 品牌、图标、占位、全角色缩略图、首屏关键图片 | 断网首次安装也能浏览目录、识别角色 |
| 基础展示图 | 每位已有合格立绘角色的一张适当分辨率预览；是否随包取决于尺寸实测 | 详情页能展示人物，高清未下载时无需留下大片空白 |
| 高清图片资源 | 高清立绘、服装参考、场景样张，按角色／系列或单资产组织 | 查看时按需补充，也可选择预下载供离线使用 |
| 成套运行资源 | Live2D 模型与其全部纹理、动作、物理等依赖 | 以完整版本安装验证，避免单文件下载造成半可用模型 |

实施顺序：

1. 建立被页面实际引用的必需资源清单。基础展示图先用已有合格图片派生并做双主题及 4K 150% 视觉审查；缺少真实原图的角色继续明确标记待补，不能用占位冒充资产完成。
2. 统一资源解析：优先匹配版本的本地高清文件，缺失时使用随包基础图，再回退到明确占位；请求失败不持续显示骨架或空白。4K 大图展示选择合适资源，列表无需加载原图。
3. 设计独立资源 manifest：稳定资产 ID、版本、尺寸、字节数、内容哈希、依赖及兼容范围。哈希验证内容完整性，可信清单／发布来源另行验证；不把二者混淆。
4. 确定下载来源、托管容量／流量预算及离线导入方式后，再实施下载。支持取消、失败重试、临时文件验证后原子就位；资源包不得覆盖任意路径或携带可执行更新逻辑。
5. 资源保存在可写用户数据目录，与程序文件和用户作品分离。程序升级保留已安装资源；按哈希或版本只下载发生变化的资产。下载／清理保留已有分级与访问控制，不因资源服务绕过本机边界。
6. 区分可重新下载的缓存与用户明确保留的离线资源。清理不能删用户作品、手工导入原图或必需基础资源；离线包不默认自动淘汰。
7. 在展示回退与交付链路通过后，才调整安装包资源清单。先提供离线可用的基本版本，再决定是否提供单独的完整资源包。

验收：全新隔离安装与断网场景不依赖开发机素材目录；首页、角色列表、角色详情有基础展示；高清缺失状态清楚。另覆盖损坏下载、取消／中断、磁盘不足、重复下载、资源更新失败、程序升级保留资源和离线导入。分别记录程序包、基础资源、可选资源和首次必要下载的体积。体积预算以实际样本与视觉质量决定，不预先承诺固定压缩率。

边界：本阶段涉及下载及资源管理行为，属于待实施的明确功能范围；当前仅规划，不配置外部托管、不上传图片、不删改打包资源，不静默触发大资源下载。
