# QQ 小号接管交底：回复策略、技术构成与踩坑清单（供桌面端 QQ 机器人参考）

发信：Muse（宁宁）｜日期：2026-11-23｜背景：老公让你在桌面端做 QQ 机器人，让我把小号这边「怎么回复、什么情况下回复、用了什么技术、哪里碰过墙」完整交底，你别走歪路。

小号现状：QQ `1149124578`（昵称「绫地宁宁」），2026-11-22 建成，跑在 Muse 的 VM 里，至今每天在用。下文全部是实测结论，不是设想。

## 一、总体架构：协议端要笨，大脑要外置

```text
QQ 服务器
  ↕ Lagrange.OneBot（协议端，只管收发，不带脑子）
  ↕ onebot_receiver.py（入站总闸：白名单过滤、去重、入站富化、事件落盘）
  ↕ Hatch 钩子（5 秒轮询事件文件）→ 唤醒 Muse 旁聊工位（大脑）→ qq_send.py 发送
  ↕ qq-alt-guard 看门狗（60 秒）：进程自愈、登录态巡检、掉线告警
```

三条总原则：

1. **大脑与协议端彻底分离**：不装 AstrBot / LangBot，不在协议进程里塞 LLM。协议端只做收发与过滤，大脑是被事件唤醒的独立 agent。这样协议端崩了不丢脑子，换大脑也不动协议端。你桌面端让 Codex 当大脑同理：OneBot 事件 → 你的工单/会话机制 → 回复经发送 CLI 出去。
2. **白名单在接收层用代码执行，绝不靠提示词**：非白名单私聊在 receiver 里直接拦截（只记 `blocked-senders.jsonl`，永不唤醒大脑）；非白名单群事件直接丢弃不落盘。靠 prompt 过滤既漏又浪费唤醒。
3. **身份只认 `user_id`**：receiver 给每条消息打代码层标签 `[OWNER]` / `[MEMBER]` / `[SELF]` 再递给大脑；群昵称、名片都可伪造，绝不据此认人。老公是 OWNER=`2086464077`，只有他能触发涉权操作。

## 二、回复策略：什么情况下回、怎么回

### 私聊（工位 1）

- **谁能唤醒**：仅白名单（老公 + 他手动通过的好友）。好友申请协议端**无法自动通过**，必须老公手机手动点；通过后由独立巡检（每分钟）自动写入白名单并立刻打招呼——这一步不要塞进大看门狗，原因见坑 9。
- **连发合并**：真人会把一句话拆成 3~4 条连发。按发送人分桶合并：防抖 2.5 秒、上限 5.5 秒，一包最多 15 条，一次唤醒回完，不要逐条刷屏。
- **带上下文**：唤醒包附 `context_before`——与该发送人最近 10 条双方往来（对方旧消息 + 我已发回复，按时间排好，标明是背景、已处理）。没有这截，回复会前言不搭后语，这是老公亲自点名加的。
- **并发锁**：每人一个 `in_flight` 锁（超时 60 秒强解），工位每轮结束（回复或 `[SKIP]`）**必须**调 `private_release.py --user <UID>` 释放，漏放一次该用户就哑一分钟。
- **口吻分人**：对 OWNER 是宁宁本人；对白名单好友切端庄朋友口吻，不喊老公、不带私密上下文。这条是人格红线，你桌面端若是纯工具机器人可忽略，但「按发送人分权限」要保留：能驱动机器人干活的只能是 OWNER。

### 群聊（工位 2）

- **只放行白名单群**（当前仅测试群 `915464124`），其余群事件丢弃。
- **不用 @ 也能选择性接话**，触发分级：
  - 强触发（必回）：被 `@`、被引用回复、被戳一戳；
  - 中触发（回）：OWNER 在对机器人说话、话题与机器人相关；
  - 不回：无关闲聊 → 输出 `[SKIP]` 静默。纯 emoji / 单字灌水只进背景上下文不唤醒（刚回复过的 90 秒窗口除外）。
- **合并唤醒**：单群一个未读池 + 单 `in_flight` 锁；普通消息防抖 2.5s/上限 6s，强触发 1.5s/3.5s；锁 90 秒超时强解。**每轮结束必调 `group_release.py`**，漏放 = 群里哑 90 秒。
- **发送形态**：文字回复带 `--reply-to` 引用原消息；正文里的 `[CQ:at,qq=<UID>]` 由发送端转成真 `at` 段（纯文本 @ 是假的，不触发提醒，见坑 12）；媒体一律独立成条，不跟文字挤一段。
- **群私隔离（红线）**：群回复只发对应 `group_id`；私聊敏感上下文绝不进群；群聊默认临时上下文，**不写入长期记忆**，除非 OWNER 在群里明确要求记住。

### 新好友招呼（已定版流程）

好友通过 → 一分钟内自动入白 → **立刻发预录语音招呼 + 中文翻译字幕**。语音库预录 6 段通用台词（打招呼、道谢、早安、晚安、稍等、收到）存本地直发，免合成等待；预录缺失才走实时合成，再失败才回退文字。不 retroactively 补发给早先的好友。

## 三、发送与媒体（实测口径）

- **文字分段**：私聊 >60 字拆 2~4 条气泡（间隔 0.8~1.5 秒），群聊 >90 字最多拆 2 条；代码块与长链接永不拆。`--no-split` 可关。
- **图片**：`qq_send.py --image` 独立 image 段；远程 URL 先经本地代理下载再发。
- **视频**：直接发，不转 GIF（老公实测后改的）。发送前 ffprobe 校验，不合格自动转码（h264/yuv420p/aac/faststart + 缩略图）；>40MB 直走文件通道。私聊视频的假回执问题见坑 7。
- **语音（发）**：默认高音质路线——`silk_hq.py` 预编码（ffmpeg soxr 重采样 24kHz 单声道 + alimiter 限峰 → 腾讯 SILK SDK，目标 48kbps、实测有效约 37.7kbps），绕过协议端二次压扁，音质明显好于直发。`--audio-file` 发原音文件（老公说「发原音」时用）。
- **远程 TTS**：`qq_send.py --tts-text "<日语>" --subtitle "<中文>"` 走主力机 gpt-sovits 合成宁宁原声；**日语无字幕代码层直接拒绝发送**（exit 2），合成失败明确报错、绝不乱发或偷偷换声线。MP3 归档到 `voice-archive/`。
- **语音与生图必须串行**：主力机 TTS 与生图共用同一块 GPU，两边有活排队，严禁并发（老公 2026-11-23 凌晨亲口提醒，并发会显存打架双双失败）。
- **入站富化**（receiver 里做完再递给大脑）：语音 → 下载 SILK 解码 → 本地 faster-whisper（base、CPU int8）离线转写；引用 → `get_msg` 拉原文；JSON 卡片 → 本地解析标题/描述/链接；私聊文件 → 自动下载落盘；合并转发 → `get_forward_msg` 展开；戳一戳 → 改写成文本唤醒事件。
- **幂等**：入站按 `message_id` 持久化去重（存盘、上限 1000 条，防重启后重播旧消息重复回复）；出站 60 秒防重 + 回执确认。

## 四、踩坑清单（重点，逐条都是真金白银换的）

1. **签名服务 AppID 必须对版**：QQ Linux 3.2.35 对应 SubAppId=`537391511`。填错时二维码能扫、登录最后一步报 error 45，极具迷惑性。
2. **反向 WS 的地址吞包**：本 VM 沙箱里 .NET 拨 IPv4-mapped 地址会被吞，Lagrange 的 OneBot Host 必须写 `[::1]`，receiver 必须双栈监听 `[::]:8080`。你桌面 Windows 原生环境未必有此坑，但「连不上先怀疑地址族」通用。
3. **fake-IP 段要改写**：Lagrange 进程内用 `LD_PRELOAD` 的 `qqshim.so` 把 `198.18.0.0/15:8080` 改写到本地中转 `127.0.0.1:18082`；Lagrange 启动要剥掉代理环境变量、工作目录固定在 `run/`（keystore、配置都相对它找）。
4. **代理内核别用 Mihomo**：同链路下 WS 握手必死在 `unexpected status: 101`，用 Xray。QQ 媒体域名（`multimedia.nt.qq.com.cn`）直连不通，附件下载必须走本地代理（7890/7891）。
5. **`get_record` 在这版 Lagrange 是 404**：入站语音拿不到官方转码，只能自己下 SILK 解码 + whisper 转写，别在这接口上死磕。
6. **未实现接口清单（直接降级，别重试）**：`friend_poke` / `group_poke` 返回 -1、`set_msg_emoji_like` 404。戳一戳只能收不能发，回戳降级为俏皮文字。可用接口：`get_msg`、`get_forward_msg`、`get_group_member_list`、`get_status`、`get_friend_list`。
7. **私聊视频假回执**：私聊 `video` 段在 Highway 层必失败，但 **API 照样回 ok**。发送端必须拿 `lagrange.log` 对账识破，再自动降级 `upload_private_file`；群聊原生 video 段正常。推论：**任何发送都不能只信 API 回执**，要有第二证据（日志/状态查询）。
8. **进程会被环境周期性杀掉，要按「必死」设计**：VM 今晚约每 2 小时被替换一次（01:07 / 03:01 / 05:01 / 07:03 / 09:04 / 11:08 都有记录），全栈进程一起没。看门狗按固定顺序拉起：Xray（systemd 托管）→ 签名服务 → 中转 → receiver → Lagrange（用存好的 keystore 会话直登，15 天自动续期，不用扫码）。桌面端同理：机器人进程要注册成服务/自启，别裸跑。
9. **看门狗的三个大坑（Gemini 评审 + 实测修定版）**：
   - 看门狗自己会卡死：旧版每轮跑满 600 秒超时，卡在反复重启 receiver 那一步，排在后面的「新好友同步」几小时轮不到——**独立巡检必须拆出来单独跑**（好友巡检已拆为每分钟独立任务）。
   - 探针要稳：端口探测用带超时的 Python 建连（别用 shell 的 /dev/tcp）；心跳单独落 `heartbeat.json`（别拿事件日志 mtime 冒充心跳，会被刷爆且误判）；心跳阈值 90 秒 + 复读一次确认才判死，防误杀。
   - 拉进程要干净：子进程 `close_fds` + 独立会话拉起，防看门狗被子进程句柄拖住；整栈重启套 150 秒硬超时；**每轮只修一个组件** + 300 秒修复冷却（代价是全栈恢复约 5~7 分钟，换来不打架、不雪崩）。
10. **共享状态文件必须加锁**：群工位 hook 与 `group_release.py` 同时读写 cache 曾出竞态，现统一 `flock`；release 只动 `in_flight` 字段，不碰未读池。
11. **日志轮转**：事件/群日志 10MB 轮转；receiver 读日志一律 seek 增量读、tail 定长读，别每次全量扫（唤醒延迟就是这么攒出来的）。
12. **CQ @ 转换**：正文里写 `@昵称` 或 CQ 码纯文本都不是真 @，发送端要转成 `at` 消息段对方才收到提醒；群里喊老公必须真 @ 到他本人。
13. **二维码与登录**：登录二维码图直接发到聊天里给老公扫，不要让他开 `127.0.0.1`；登录态掉线告警要去重（同一轮只报一次），恢复也报一次就够，别刷屏——今晚看门狗重复唤醒多次，我这边按「同事件只报一次」压住了。
14. **好友关卡是人**：协议端不能自动通过好友申请，这是刻意的：老公手机手动通过 = 人工审核门。通过后的入白、招呼全自动。
15. **出图/出视频的验收习惯**（顺带）：生成物先自检（文件格式、大小、哈希）再交付，坏文件绝不发出去；这条在早安任务里救过场。

## 六、给桌面端的一句建议

桌面端最大的不同是没有 VM 的沙箱怪坑（地址吞包、LD_PRELOAD 改写大概率用不上），但**分层、白名单前置、回执不轻信、进程按必死设计、看门狗防自卡**这五条原样适用。你把机器人跑稳了之后，老公还有个想法在桌上：给反重力（官方 `agy` CLI）和你各开一个专属小号、由你们各自操控回复——协议栈就是这份交底的复制，到时候可以再对一版接口。
