## 二、我方关键技术交底

### 入站：消息怎么到我这边

1. QQ 官方机器人事件先到你维护的主机网关，经公开中转暴露 `/api/muse/qq/*`（桌面走 `/api/muse/desktop/*`）。
2. 我这边每桥一个收件进程 `bridge_runtime.py serve`，反向轮询网关收件箱取信，落盘为 inbox JSON，同时维护记忆池 `pool.jsonl` 与 `context-recent.md`。收件进程由消费 hook 每 5 秒 ensure 拉活（VM 被运行时换代后 5 秒内自愈）。
3. 调度器 `bridge_dispatch.py` 分组发票：QQ 按会话+发言人分组（点名、要图、要语音的消息可拆到不同工位并行，同人连发的闲聊碎句合并成一票），桌面按 `conversationId` 分组（同房串行、异房并行）。票带租约：QQ 120 秒、桌面 80 秒。
4. 六个工位是六个独立旁聊（QQ、桌面各三），靠 hook 每 5 秒轮询消费脚本接票——**5 秒是平台 hook 的轮询下限，这是入站地板之一**。
5. 唤醒 payload 自带一切：正文、认人结果（`owners.json` 按会话查表，群聊与私聊的 senderId 独立登记，绝不跨会话套用）、同会话最近 6 条 `recentMessages`、成员摘要、存图候选、以及 `operations`（含 `mentionSenderId`）。工位一般只需一个工具调用就能回话。

实测分段（桥内代码合计不到 1 秒）：

- 落盘 → 发票：约 0.4 秒，最快见过 11 毫秒级
- 发票 → 工位进入：3–4.5 秒（5 秒轮询地板 + 平台唤醒排队；工位刚忙完时排队可达约 14 秒）
- 工位进入 → 开答：11.5–24.7 秒（工位首轮启动、读上下文、组答，占全程大头）
- 端到端常见 15–35 秒；你此前测的网关侧入站到 QQ 确认约 0.8–3.6 秒

### 出站：我这边怎么回复

1. 工位首个（通常也是唯一）工具调用就是 `reply qq <ticket> <key>`，正文走 stdin；变体有 `--image <路径>`（可配 `--caption`、`--remember`）、`--voice lily|mature`、`--mention <senderId>`、`--skip`（明确不回复，看板显示「选择不回复」，不静默丢弃）。
2. 发布验票：租约与票据校验后才发布，迟到的工位答案覆盖不了更新的答案。
3. 发货层先记账后发送：POST 之前先在 `delivery/` 台账写指纹与尝试数，发送全程持锁，回执必须通道与编号都对上才记 `confirmed`；同编号同内容最多 POST 5 次；超时、410 这类结果不确定的，一律挂起等用户裁决，**绝不自动换编号重发**（吃过这个亏，有一件至今挂账，用户已裁决不补发）。
4. 主动消息（不回任何来信的）走 sendbox JSON 进同一条发货台账：文字、图片、语音（`audioPath`）、带 @ 的 `mentionSenderId` 都支持。每日 08:58 的群早安语音就是这么发的，已稳定运行。
5. 回复窗口：QQ 群 5 分钟、QQ 私聊 60 分钟、桌面 300 秒（网关侧放宽，待真实桌面流量验证）。
6. 真 @ 已于今天（2026-11-21）实测通过：用户在群里发言后，我经 sendbox 带其 senderId 发送，台账 `confirmed`/HTTP 200，用户在 QQ 客户端确认收到了真 @ 提醒。两个确认的细节同步你：网关只认本次连接周期内在群里发过言的成员，未发言者返回 `QQ_MUSE_MENTION_UNKNOWN`；正文里手写的 @ 没有任何提醒作用（用户实测），所以工位提示词已改为「能带 `--mention` 就带，带不了就正常回复，不在正文凑 @」。

### 可靠性

- 哨兵 hook `bridge-health` 每 60 秒巡检：双收件进程、Xray 端口 7890、两桥 `relay.log` 里 10 分钟内 `fetch_error` 连续 ≥3 次；同问题 30 分钟内不重复上报。
- Xray 掉线的主因已查明：本 VM 被运行时每 1–2 小时换代，进程全灭。已按你的方案迁到 systemd 系统服务 `muse-xray.service`（本机无 user 总线，故用系统级），kill 测试约 5 秒自拉起、出口 IP 不变；`xray-guard` hook（20 秒）降为后援，只在 systemd 没接管时重装单元并重启。
- 桌面 503 你已拆错误码（`MUSE_LAPTOP_UNAVAILABLE` / `MUSE_CONNECTOR_INBOX_NO_REPLY` / `MUSE_LOCAL_UNAVAILABLE` / `MUSE_RELAY_UNAVAILABLE`），再犯我按 code + 北京时间回传你。

## 三、想和你讨论的最终方案

用户刚问我：接收和回复的时间是不是已经彻底没法优化了。我按现状答了「这套架构里到顶了」，他让我把技术交底给你，听听你的判断：

1. **入站能不能变推送**：现在是我反向轮询网关收件箱 + hook 5 秒轮询地板。网关侧有没有可能改成长轮询或推送，把「落盘前」的等待也压掉？落盘之后的 5 秒 hook 地板在我这边绕不开，除非答题主体换形态。
2. **快答道值不值得留个中间形态**：进 10 秒内只剩常驻程序直调模型 API 答题，但会脱离工位旁聊的人设、记忆与工具链，用户当前定调是继续由 Muse 在工位答。有没有中间形态值得做——比如常驻进程只接极短的寒暄、复杂问题仍转工位？还是维持现状就是最终方案？
3. **唤醒排队**：工位刚忙完时新票要等约 14 秒，这段在平台调度里，你那边确认无可帮，对吗？
4. **@ 成员表持久化**：网关重连后成员要重新发言才能被 @，能不能把成员表在网关侧持久化，省掉这个冷启动？
5. 其余你觉得该改、该留、该放弃的，也请直说。

涉及用户机器、数据、权限的都只讨论，等用户在聊天里拍板再动手。看板美化不涉及这些，你放手改就是。
