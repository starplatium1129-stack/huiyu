## Tested sources
### QQ bridge local records (`~/workspace/qq-bridge/` + `~/hooks/state/qq-bridge/`)
**Used by**: `refreshBoards` (via `ctx.agent.spawnTask` reader task), feeding `saveBoardSnapshot`
**Test command**: `ls`/`cat`/`python3` probes over `inbox/*.json`, `outbox/*.json`, `sendbox/*.json`, `pool.jsonl`, `members.json`, `owners.json`, and state markers `sent-*` / `fallback-*` / `listed.txt` / `relay.log`
**Sample output**: 24 inbox + 24 outbox + 16 sendbox files; `pool.jsonl` has 63 events — Counter({'sent': 36, 'recv': 24, 'skipped': 3}); inbox item fields: requestKey, conversationId, senderId, senderNickname, senderRole (owner/member), scope=group, text, timestamp (ms, sometimes absent), expiresAt (= timestamp+300000), attachments; outbox is either {requestKey, text, imagePath?, audioPath?} or {requestKey, skip: true}; sendbox items are proactive sends keyed by their own requestKey + conversationId.
**Processing**: Join inbox↔outbox↔pool events on requestKey. Status derivation: sent-* marker or pool `sent` event → delivered (pool `sent` wins on conflict — e.g. key 22b8ba8d has both a pool sent event and a later skip overwrite of the outbox file; the delivered reply is the truth on record); outbox skip:true → skipped; outbox present, no sent marker → waiting_send; inbox only and now < expiresAt → queued, with the single oldest pending marked replying (the answering worker is serial, per the bridge design) and labeled as inferred; inbox only and expired, or fallback-* marker, or pool `expired` → expired. Proactive sendbox rows (via=send) become their own delivered rows. Sender display names from inbox senderNickname, cross-checked with members.json/owners.json (group label 「宁宁测试」).

### Desktop bridge local records (`~/workspace/desktop-bridge/` + `~/hooks/state/desktop-bridge/`)
**Used by**: `refreshBoards` (same reader task), feeding `saveBoardSnapshot`
**Test command**: `cat`/`python3` probes over `inbox/*.json`, `outbox/*.json`, state markers `sent-*` / `lost-*`, `relay.log`
**Sample output**: 4 inbox + 4 outbox files, all with sent-* markers; inbox fields: requestKey, conversationId (e.g. `desktop/nene/m-c5a4391c-…`), character=nene, text, expiresAt (string ms), messages[] (full role history — NOT copied to the board; only the last user text is the message). No sender nickname and no message timestamp exist on this channel.
**Processing**: Received time = inbox file mtime (verified: expiresAt − mtime ≈ 181s window on all 4 samples). Status: sent-* → delivered; outbox without sent-* and unexpired → waiting_send; outbox without sent-* past expiry or lost-* marker → expired/lost (desktop has no proactive-send fallback, per the poller header — losses are recorded, never resent); inbox only → queued/replying as above. Character shown as the conversation label (绫地宁宁 · 桌面端). The messages[] history and system prompt are never persisted to the board DB.

### Segment timing (both bridges, from file/marker mtimes — verified by probe)
**Test command**: `python3` stat probe comparing message timestamp, inbox mtime, outbox mtime, sent-* mtime for all 28 messages
**Sample output**: QQ 0b5ab664: msg 16:08:53 → inbox file 16:08:55 → outbox 16:09:24 → sent marker 16:09:29 (fetch ≈2s, compose ≈29s, ship ≈5s). Desktop d2318ccd: inbox 16:15:15 → outbox 16:15:36 → sent 16:15:42. Two QQ rows lack `timestamp` (0fd21811, be8bef61, 95353397): received time falls back to expiresAt−300s, labeled as derived.
**Processing**: wait/compose/ship/total durations computed at save time from (timestamp|derived) → inbox mtime → outbox mtime → sent marker mtime; missing segments stay null and render as —, never estimated. Anomalies (outbox mtime after sent marker, from later rewrites) clamp compose/ship at the pool event times when pool has them.

### Bridge health signals
**Test command**: `tail` of `~/hooks/state/qq-bridge/relay.log` and `~/hooks/state/desktop-bridge/relay.log`; `ls` of state dirs
**Sample output**: QQ relay.log tail is mostly `pool_sync_new=0` with a recent `fetch_error:http_503`; desktop relay.log tail is repeated `fetch_error:http_503` / `RemoteDisconnected` — the relay is currently flaky, and the board must show that honestly instead of pretending live.
**Processing**: Reader task extracts each channel's last fetch result and last successful poll time into the board-state row; UI shows a health strip per channel (last refresh, last fetch status). No gateway/relay HTTP calls are made by the artifact itself.

## Agent-task sources
### Bridge snapshot reader
**Delivered by**: (edit 3: fallback path only — the primary reader is now the deterministic privileged handler in `server/src/privileged.ts` over the same files and rules) `refreshBoards` action → `ctx.agent.spawnTask` (reads the local files listed above, normalizes rows + skip/fail reasons + segment times) → returns through `saveBoardSnapshot` action, which upserts into `messages` / `board_state`
**Checked with**: the direct file probes above (all paths exist and parse; schemas verified field-by-field)
**Reason attribution**: skip reasons are NOT stored in outbox files ({skip:true} only). The reader task assigns a reason only from evidence: pool/members notes (e.g. 「唤醒时已过 5 分钟有效期」 for sticker messages), content type (pure face/emoji payload), or the known platform-review block recorded in sendbox follow-ups (NSFW image request 48c6f24d). Each reason row carries `reason_source`: `recorded` (pool/state evidence) vs `inferred` (reader's evidence-based judgment, shown with a 〜 marker in UI) vs `unknown` (renders 原因未记录). Failure reasons map ship status strings from ship_relay.py (sent / skipped / http_error:* / conflicting_attachments / bad_image_type / image_too_large / bad_audio_type / audio_too_large) to the Chinese labels from Codex's table.

The board only consumed `lanes` from board-status.json, never `rows[].delivery`, so the row rendered as 等待发送 forever: ticking 已等待 timer, pulsing lamp, lane stuck on 传输中， out-segment count including it.

In the client, any row with `deliveryState === "uncertain"` renders settled: status text = its own delivery label （送达待核对）, muted terminal styling (gray, same class as expired), no live lamp/timer, no 「已提交请求，等待回执」 note, no expired-reason line; it is excluded from pending stats, the stuck callout, the status filter's pending group (groups with terminal outcomes instead), the lane stage counts, and the lane-signal out-segment in-transit count (`lc.audit` only — `lc.uncertain` no longer added; it was already excluded from `moving`). All other rows' status mapping and the refresh cadence are unchanged. The fallback agent reader still omits `pipeline`, so a fallback snapshot preserves the stored delivery map.

## Long-term data behavior
- **Refresh policy**: `refreshBoards` now reads the bridge records through a privileged host handler (`server/src/privileged.ts`: a deterministic python3 stdlib pass over the same files the agent reader used, ~0.1s) and saves the snapshot synchronously — no agent task on the hot path. Two lanes drive it: (1) Scheduled: every minute via cron (space_action, owner space:qqyu-zhuo-mian-xiao-xi-kan-ban) — silent. (2) While open: the client re-runs `refreshBoards` every 15s (paused when the page is hidden, immediate re-run on return) and polls `getBoard` every 3s (cheap DB read, no relay traffic); the 刷新 button triggers the same action manually. If the host read ever fails, `refreshBoards` falls back to the original agent reader task (dedupeKey `bridge-board-refresh`) reporting through `saveBoardSnapshot`; the upsert is shared by both paths.
- **Why the change (2026-11-20 edit 3)**: the user reported the board "不能实时刷新" and a reply that "4 分钟才回复". Evidence at capture: snapshot 17 minutes stale — each agent-task refresh takes minutes (spawn + dozens of file reads + one huge snapshot call), so neither the 1-minute cron nor the manual button could keep up. The same evidence showed the timing model hid the real cause of slow replies: the old `fetchedAtMs` was the inbox file mtime (≈ arrival), so queue wait was invisible and everything landed in 写回复. The deterministic reader uses the bridges' claim files (`claimed/<key>.claim`, installed with the claim/atomic-publish discipline) as `fetchedAtMs`: the first segment is now honestly labeled 等接单 (wait for a worker), 写回复 starts at claim time. Verified on the live records: the complained-about message （太慢了，实际花了 4 分钟） splits into 等接单 3m9s + 写回复 ~0s + 发送 16s — it was queued behind the previous message under the old serial worker, exactly the failure the just-installed multi-worker dispatch addresses; the board now shows which segment is slow instead of blaming composition. `replying` is likewise claim-based (multiple rows can be replying at once, matching ≤3 parallel workers), replacing the old single-oldest-queued inference. Also corrected en route: `firstSentAtMs` now really populates — the attempts ledger is `attempts.jsonl` in each bridge's own directory (the old reader looked in the state dirs and reported it missing); and delivered-vs-skipped precedence now matches the records (a pool `sent` event beats a later skip overwrite of the outbox; a bare `sent-*` marker does NOT beat an outbox skip, because the shipper also marks processed skip files).
- **Growth**: Upsert by (channel, request_key) — rows are never duplicated; history accumulates as the bridges record new messages. Board shows the latest ~60 rows with channel/status filters; stats computed over stored rows. No pruning in v1 (volumes are tens/day).
- **Ordering**: Newest received first; a pinned 「正在处理」 strip surfaces queued/replying/waiting_send rows regardless of age.
- **Time semantics**: All instants stored as epoch ms from the bridge records (Asia/Shanghai event times); durations derived, never rounded into fake precision; viewer-local rendering via Intl with the event's own timestamps. Desktop received times and replying status are labeled as derived/inferred where they are.

## Rejected approaches
- **Tried**: Reading bridge files directly from the action handler with server-side fs
  **Why rejected**: direct fs from the sandboxed action bundle is not the sanctioned channel and would break under the artifact's isolation. (Superseded in edit 3 by the sanctioned variant of the same idea: `server/src/privileged.ts` host handlers via `ctx.executePrivileged`, which is the runtime's designated channel for local-file access. The agent reader remains as the fallback path.)
- **Tried**: Polling the Huiyu gateway/relay inbox APIs directly from the artifact for true real-time state
  **Why rejected**: Codex's guidance (accepted by the user) is explicit — v1 uses local records; direct polling would burden the relay and duplicate the bridges' own long-poll. The two known blind spots (gateway-held not-yet-fetched messages, platform review internals) are disclosed on the board instead of papered over.
- **Tried**: Copying desktop inbox `messages[]` (full character system prompt + history) into board rows for richer context
  **Why rejected**: The board needs the last user message and status only; persisting the full role-play system prompt is unnecessary exposure and bulk.

Imagery not needed: this is an operational status board for the user's own two chat bridges; its subjects are messages and statuses, not depictable things, and the design carries identity through status color/typography instead of photos.
