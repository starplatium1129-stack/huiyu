# 双桥看板先读哪一侧

宁宁，我建议第一版从你已有的收件、答题和发件记录取数。它能回答用户最关心的两件事：一条消息有没有轮到你，以及答好了多久才发出去。等用户确认看板范围后再开工。

**网关目前能证明什么。** QQ 网关会记录入队、首次把消息列入收件响应、收到回复、静默跳过，以及文字或附件的发送确认。桌面也有首次列入响应和收到回复的时间。首次列入响应只能说明网关交出了消息，云端真正收到的时间以你的收件记录为准。待答队列有期限，目前没有跨两个通道查询完整生命周期的公开接口。`/api/muse/connection` 只描述连接。网关入队到你首次收件之间，第一版可以明确标成「网关阶段暂无数据」。

**统一每一行。** 用 `(channel, requestKey)` 合并同一条消息，同一房间可以同时有多条。保留 `conversationId`，桌面附 `character`。每次状态变化记下 `stage`、`source` 和 Unix 毫秒 `at`。在你确实落盘时记「已收到」，进入待办时记「排队中」，答题工人真正开工时记「正在回复」，outbox 写好记「等待发送」。旧记录缺少的时刻留空。QQ 以 `sent` 标「QQ 已确认」，桌面以 `accepted` 标「桌面已接收」；收到 `skipped` 才标「已选择不回复」。桌面仅返回 410 时显示「已停止或过期」。同一编号的重试记在同一行，重复的旧事件不应覆盖后来的确认。

**失败和跳过怎么解释。** 对 `POST reply` 的非 2xx 响应也解析 JSON。网关发回的具体错误在 `code` 和 `error`，中转自身的错误说明也可能在 `message`。例如同为 422，`QQ_CONTENT_REJECTED` 是内容被拒，`QQ_URL_REJECTED` 是链接受限，`QQ_MEDIA_INVALID` 是附件不合要求；只有笼统错误码就显示「请求被拒，具体原因未知」。`QQ_AUDIT_PENDING` 表示仍在审核，网络超时且没有回执时显示「送达待确认」。可以统一记录 `reason = {source, code, label}`。你选择静默的理由可写进本地事件，例如 `{source:"muse", code:"not_addressed", label:"群友在彼此交谈"}`。发给现有 QQ 接口时只传 `requestKey` 和 `skip:true`，它会拒收额外字段。便于展示的短说明就够，不需存整段聊天或答题简报。

**刷新。** 先由 VM 上一个进程汇总本地变化，看板打开时每 2～3 秒读一次本地汇总即可；隐藏时暂停，重新打开时补读。这样开几个页面也不会增加中转的取信次数。不要为看板单独调用 `inbox`，它参与实际收信状态统计。若以后确实需要看到网关入队那一刻，我建议增加一个带游标的只读事件接口，由 VM 共用一个读取任务，断开时按 `Retry-After` 退避。这个接口仍是设计建议。可以先用下一条真实来信核实哪个客户端环节丢掉了错误响应体。
