# 架构治理、文档与运维审计

基线：`39d955e6186e16f68f30b8b7d74136d88b896a43`，2026-09-20。本报告关注职责、证据和维护入口；源码中的具体故障分别见 [前端](frontend-ux-accessibility.md)、[性能与维护性](performance-maintainability.md)、[后端与桌面](backend-desktop.md)、[存储](storage-functional-reliability.md)。

## 当前架构与已有保障

基线 Git 跟踪 2,886 个文件，其中 Vue 组件 123、前端 TypeScript 474（含 153 份测试）、routes TypeScript 49、server TypeScript 45、services TypeScript 12、桌面 Rust 源 28；这些是文件计数，不是有效代码行数或复杂度评级。数据聚合、生成 JavaScript、模型及运行目录大量被忽略，不能用 Git 文件数估算安装体积。

实际职责链为 Vue 页面 → composable/store/usecase → API 或存储适配器 → Express 网关/任务服务 → 本机或配置上游；桌面壳另管进程、原生窗口与 Live2D 渲染。TypeScript 源编译到兼容的 `.js` 入口，源码/产物一致性、单体预算和部分领域依赖有门禁。场景源分片、派生产物、候选资产、人工审核与不可变发布也已区分。

不建议为“全面审计”整体换框架、把 IndexedDB 全迁 SQLite，或重写已经稳定的渲染/生成管线。先修确认缺陷，再按同一业务路径收拢授权、取消、持久化和恢复契约；每次抽取保留真实行为对照。

## GOV-01 · P2 · 用户文档的“全自动”表述与人工发布契约不一致

**证据：确认。** `README.md:29`、`README_zh.md:29` 将参考库描述为自动闭环/全自动自愈；`docs/workflow.md` 的“参考库候选审核与版本发布”明确要求候选、人工决定、记录/图片/输入版本核对和显式 apply。已有生成/视觉检查自动化不等于内容获准发布。

影响：用户可能把自动检查、已填写 URL 或候选生成成功理解为实物审核和发布完成；英文和中文使用说明还可能把旧引擎/并发配置当成当前默认能力。

落实步骤：

1. 从当前注册表和执行代码列出生成、自动质检、人工决定、发布四个阶段及实际输入输出。
2. 同步修订两份 README 的能力陈述，链接工作流和当前状态；避免在多份文档重复容易变化的模型版本、并发数、资产数量。
3. 对一个中性候选走 `--plan`/预览，确认缺人工决定确实保持 pending；不为了文档审阅调用模型。
4. 运行 `docs:check`，按首次使用者视角核对“下一步”和“完成”的含义。回退只涉及文档，不改变发布门控。

## GOV-02 · P2 · 工程契约中的主题接入说明落后于运行时实现

**证据：确认。** `docs/engineering-contracts.md:30` 仍要求给每个新角色写专属 CSS 选择器；`src/utils/characterTheme.ts`、`tokens.css` 的通用契约和 `docs/workflow.md` 的主题影响报告已经支持运行时数据/调校目录。当前全域主题覆盖报告也以运行时契约判定，而非强制一角色一段 CSS。

影响：后续维护者可能重复添加静态主题，增加令牌分叉，或者把已有通用主题误判为未接入。

落实步骤：

1. 明确通用主题的必需数据、调校例外、缺失/非法值回退和对比度规则；列出唯一权威入口。
2. 将角色接入第 2 项改为检查运行时主题契约和实际深浅主题效果；仅特殊调校新增例外。
3. 选普通角色、默认角色、缺强调色和非法强调色四个夹具验证报告/渲染保持一致。
4. 继续要求实际 AA 和图片叠字审查，不能用结构检查替代视觉。只改文档时运行链接和规则一致性检查；修改主题实现时按 UI 范围验收。

## GOV-03 · P2 · 历史修复专用工作流仍持有写权限

**证据：确认配置存在，未证明已被利用。** `.github/workflows/audit-stability-validation.yml:4` 只监听一个专用旧分支，`:6` 赋予 `contents: write`，后续运行 PoC、自动暂存固定业务/数据文件并 push。它不由本次 main 文档提交触发，不能描述成 main 每次运行都会自动改代码。相比当前常规只读质量工作流，这是额外的长期维护入口。

落实步骤：

1. 核对旧分支任务是否结束、是否仍被实际使用，保留其修复提交与历史 Actions 证据。
2. 若已完成，移除专用自动写入工作流及失去用途的 PoC，复核孤儿脚本规则；若必须保留，改为生成可审核补丁或 artifact，取消自动 push。
3. 将权限降到任务实际所需并关闭 checkout 的凭据持久化；保留现有 Action SHA 固定策略。
4. 验收触发矩阵：main/普通 PR 不触发写入；人工运行只能产生声明产物。单独提交清理，必要时从历史恢复，不保留不透明后台写路径。

[GitHub 官方安全指南](https://docs.github.com/en/actions/reference/security/secure-use) 建议限制 token 权限并固定依赖的 Action 版本；仓库普通 CI 已落实其中多项，本项针对历史例外。

## GOV-04 · P2 · 发布证据需要从“日志位置”升级为可长期核验的摘要

**证据：覆盖与可移交性风险。** 很多最新状态记录引用被忽略的 `runtime/...` 目录。已有 `capture:delivery`、`audit:delivery`、源码/构建哈希和失效机制，本轮不重新发明格式；但仅链接本机路径不能让另一台机器核验日志仍存在、属于哪个构建和哪些设备条件。

落实步骤：

1. 对下一次真实交付复用现有回执，明确 source commit、构建 SHA、运行环境、实际命令、失败/跳过、素材模式。
2. 挑选脱敏的摘要和关键失败/通过记录入仓或放入既有受控 artifact；原始大图/日志按现有资产规则存储，不将运行配置、密钥或私有模型带入 Git。
3. 在主力机使用 `audit:delivery` 比较共同构建标识，独立登记 installation/deviceAcceptance/modelAcceptance，不能只比较 HEAD 就关闭全部待办。
4. 验收：改动被选择的源码、构建或日志后旧证据变 stale；缺少设备记录仍为 pending。回滚采用上一份已知构建和对应回执，不能用新代码引用旧截图。

本次随报告提交 [脱敏证据摘要](evidence.json)，它保留失败结果和日志哈希，不认证日志语义，也不替代未执行设备验收。

## GOV-05 · P3 · 入口检查通过不等于描述、锚点和条件全部正确

**证据：确认检查口径。** 报告编写前 `docs:check` 检查 207 个 Markdown/HTML、1,228 个本地链接和 60 个重定向，0 断链。`audit:workflow-conditions --json` 对 103 个命令报告 ok，执行状态全为 `not-run`。`check-doc-links.ts:25` 会移除 URL fragment 后检查文件，故错误的同页标题锚点不一定报错；外部链接和文档语义亦未由它验证。

落实：保持轻量链接检查，另对日常八入口和新报告做规则一致性审查；若锚点失效实际频繁出现，再增加 Markdown heading/HTML id 校验与中英文标题夹具。不要因为“检查通过”就宣称所有操作可运行，也不应为文档提交启动模型、安装器或全量生成。

## 推进方式与停止条件

优先级按真实影响安排：远程边界、用户数据覆盖、结果恢复和构建阻断先于视觉重排与普遍抽象。改进计划按 [分批实施表](implementation-plan.md) 执行，每批声明文件范围、责任角色、失败行为、验收与回退；完成后只在 roadmap 关闭对应条目，历史审计结论保留日期，不反向改成一直通过。

本轮没有检查 GitHub main 规则配置、外部作者授权原件、私有模型许可证全文、物理断电恢复或主力机 GPU/安装状态。数据中的作者/terms 字段是登记事实，不是授权核验结论；需要再分发时应补原始来源与具体版本证据，不作无证据的法律判断。
