# 用户数据、恢复与功能闭环审计

审计日期：2026-09-20。受审基线为本次综合审计开始时的 `main@39d955e`。已先读 `AGENTS.md`、工程契约、工作流和 roadmap。本报告审查作品/项目/回收站、图片持久化、备份恢复、跨窗口、任务摘要与生成结果保存；未访问用户实际 IndexedDB/localStorage，未调用真实模型或发布安装包。

## 结论与范围

作品库已有 Web Locks、IndexedDB 事务、软删除、引用重扫、暂存保护和失败补偿，不能按早期历史报告将这些保障写成缺失。本次重点发现是：合并恢复期间的旧 localStorage 快照可覆盖并发聊天写入，以及备份预检允许导入运行时无法展示的历史记录。另有跨存储崩溃恢复、大备份、跨窗口任务摘要和清理诊断边界需要分批落实。

方法为源码与既有测试审查、生产纯函数最小输入探针、生产恢复代码的内存适配器故障时序探针。全量 gate、浏览器和后端专项的当次结果见[综合报告](README.md)；本报告不将已存在的测试文件当作当次 PASS，不重复报告后端结果首次读取即消费的问题。

## 现有保障与数据边界

| 范围 | 当前机制 | 边界 |
| --- | --- | --- |
| 作品/项目修改 | `artworkMutation.ts:5` 同源 Web Lock；KV 多键事务等待 `oncomplete` | 必须所有写者遵守协议；不能控制旧窗口/外部写者 |
| 图片原件 | 独立 IndexedDB Blob；`useImageStore.ts:65` 等事务完成 | 与 KV、localStorage 不属于同一事务 |
| 删除/撤销 | 默认软删 30 天；history/projects/trash 原子发布 | 过期清理仍需引用可读且取得跨文档独占 |
| 孤儿清理 | 确认只授权当次 ID；执行前重扫作品、项目、回收站、隔离区及草稿 | 多窗口或读失败时拒绝删除；不放宽草稿保护 |
| 图片暂存 | `artworkSession.ts:72` 在图片创建至引用发布之间持共享锁 | 防止清理误删，不能代替结果提交事务 |
| 备份导出 | 512 MiB 双向上限，逐图编码、进度及取消 | 全量 JSON 格式；不是恒定内存或分卷方案 |
| 恢复 | 新 image ID 暂存，重映射引用，KV 批量发布；保留原图 | 设置写入与 KV/图片跨存储，需要单独恢复协议 |
| 聊天 | mid 合并、角色清空修订、独立草稿/音量键 | 不持作品库 Web Lock；普通设置允许最后写入覆盖 |
| 任务中心 | 持久化摘要，刷新后 running 标为 interrupted | 摘要不是持久任务执行器；不会自动补发生成 |
| 旧作品配方 | 只读解析，缺 seed/prompt 明确提示不能精确复现 | 保存时默认值不是历史生成事实 |

备份明确只打包作品历史、项目、白名单 localStorage 和图片：`src/utils/storageKeys.ts:56` 起列出的回收站、隔离区、sessionStorage 临时结果/视频草稿、队列快照有显式排除规则。它们不应被误报为“无意漏导”。但产品说明仍应告诉用户备份可恢复哪些内容；含 Blob 不代表可恢复其原始临时会话。

## 发现与具体落实步骤

### STORE-01 · P1 · 合并恢复会用旧快照覆盖其他窗口的新聊天

**证据。** `src/storage/backupRestore.ts:28` 收集全部活跃设置并计算 nextSettings，`:53` 逐图异步暂存，`:57` 回写整份设置。`writeSettings` 在 `:15` 对 nextSettings 的全部键执行 setItem。恢复只持作品库写锁，`src/composables/chat/useChatStorage.ts:355` 的聊天保存不使用该锁。

**当次复现。** 将真实 `restoreBackupData`、`prepareBackupSettings` 及依赖在内存转译，接入内存 localStorage/图片/KV/锁适配器：初始聊天 1 条，incoming.settings 为空；在 await imgPutRecord 期间模拟另一窗口写成 2 条；合并恢复返回后变回 1 条。主题键相同探针也从并发新值退回旧值。没有读取或修改真实用户存储。置信度高；证明的是生产逻辑的确定时序，不是实际浏览器多窗口试验。

影响不仅是用户主动选择覆盖恢复；合并恢复且备份不含聊天设置时也会覆盖期间的更新。失败回滚 `:65` 回写 previousSettings 也有同类风险。

落实步骤：

1. 首先增加隔离回归：恢复暂存阶段暂停，外部写者更新聊天/草稿/设置，继续成功和失败两条分支，均不得静默覆盖后来写入。
2. 短期优先复用文档共享/独占协议，为恢复建立明确的维护区间；其他窗口存在时禁止开始需要全量设置替换的恢复。不能只增加另一个所有普通写者不持有的锁。
3. 对同窗口仍运行的聊天/偏好写入，加入修订检查或统一维护状态。合并模式仅更新备份实际涉及的键，发布前读取最新值重新合并；失败补偿只撤回自己写入且未被后来更改的键。
4. 对 replace 模式明示覆盖范围，并保证确认后至提交期间的写入隔离；保留当前完整原图不删除的规则。
5. 浏览器用原生 Web Locks、两个同源窗口复验恢复与聊天/草稿/作品保存交错；再在 WebView2 中复验。

验收：并发新消息不丢；未导入键保持最新；有冲突时明确停止或合并；失败不能回滚其他写者。回滚：恢复旧实现前保留用户备份，必要时暂时限制恢复为维护模式，不删除任何原图。

### STORE-02 · P1 · 备份预检接受运行时无法展示的历史记录

**证据。** `src/utils/backupCore.ts:53` 的 records 只检查“对象且非数组”，`:98` 因而允许空 ID/无 ID 对象；`:114` 原样接收 history。覆盖恢复 `src/storage/backupRestore.ts:58` 直接发布 importedHistory。运行时 `src/types/artwork.ts:40` 仅接收非空字符串或有限数值 ID，其他项被过滤。

**当次复现。** 调用真实 `normalizeBackup`，schemaVersion=2 的 `history:[{id:''}]` 通过并计为 1 条；随后调用真实 `parseArtworkRecords` 得 0 条。`[{timestamp:1700000000000}]` 同样为“接受 1、可展示 0”。这是纯函数探针，未执行生产覆盖恢复。置信度高。

另一个预检边界是 `image_id:'missing-image'` 且 images=[] 仍通过。现有 `backupExport.spec.ts:66` 明确支持 records-only，因此不能直接认定所有无图备份非法，也不能为了修复而破坏兼容。问题是预览缺少“缺图/不可展示”的可恢复性说明。

落实步骤：

1. 提取“可发布历史/项目”解码与结果清单，复用当前运行时要求；现代备份空 ID、重复身份、非法项目引用应在写入前明确拒绝或隔离报告。
2. 对受支持的旧 timestamp-only 格式，定义稳定 ID 迁移及项目引用重映射，不能简单丢掉旧数据。无法无损迁移时保留原件并停止覆盖。
3. 预览分别显示可恢复记录、将隔离记录、含图记录和缺图记录；records-only 保留，但用户应看见它不包含原图。
4. 关联校验必须区分备份内图片、明确允许的现存图片引用、远程/旧格式引用。不能仅凭同名 image ID 自动把导入作品关联到当前另一张图。
5. 扩充现有 backupRestore/backupCore 回归：空 ID、重复 ID、合法数字/字符串 ID、旧格式迁移、项目引用、records-only 与 images-only。

验收：覆盖前展示的可恢复记录数等于恢复后可见记录数；不可恢复内容在任何写入之前被说明；合法旧备份仍可恢复。回滚：保持旧格式只读解析或暂停有歧义的覆盖入口，不把降级过滤当作成功恢复。

### STORE-03 · P2 · 跨图片、设置与作品库的恢复缺少持久提交日志

**证据。** `src/storage/backupRestore.ts:27` 的 stagedIds、`:28` 的 previousSettings 仅驻留内存；`:57` 先写 localStorage，`:58` 后提交 KV。catch 可处理可捕获异常，但进程在两步之间终止后没有可重入 journal。原图不删除的设计降低损害，仍可能留下新设置/旧作品和无引用新图。

这与 roadmap `:62` 起的大型恢复及设备边界相关，不应改写为“现有普通失败回滚失效”。置信度：高（持久恢复记录缺失）；实际断电后的落盘表现未测试。

落实步骤：

1. 在隔离库建立阶段故障注入：预检后、图片逐张暂存后、设置发布后、KV 提交前后、清理中终止。
2. 设计最小恢复日志：operationId、输入备份哈希、原设置快照/修订、暂存 image IDs、预期元数据摘要、phase。日志先持久化，再进行对应阶段。
3. 启动时先识别未完成恢复，按实际提交身份决定继续、撤回或要求用户确认，不能按“上次函数抛错”猜测 KV 没提交。
4. 清理只删除本事务拥有且确认未被发布/引用的图片；损坏日志保守停止，不扩大删除范围。
5. 先做浏览器关闭/强杀隔离验收，再做主力机受控测试。物理断电另列设备验证。

验收：每个中断点重启后得到完整旧状态或完整新状态，或明确的待恢复状态；没有静默混合状态和误删。回滚：保留日志兼容读取与旧原件，未完成事务不能因代码回退被当成普通孤儿直接清理。

### STORE-04 · P2 · 512 MiB 以内的大备份仍可能造成高内存峰值和不可取消恢复

**证据。** `src/utils/backupExport.ts:5` 的双向上限有效，导出逐图编码也已实现；但 `src/composables/useBackup.ts:175` 一次 file.text + JSON.parse，`src/storage/backupRestore.ts:32` 在任何写入前 map/atob 解码全部图片。恢复无逐图取消/进度接口。实际峰值取决于引擎字符串/Blob 实现，不能只以 JSON 文件大小推断可用内存。本项是 roadmap 已知“大图库/低内存、分卷或流式恢复”边界的源码复核。

落实步骤：

1. 使用合成且不含用户内容的 16/128/接近 512 MiB 包，在目标 WebView2 记录成功率、峰值内存、主线程停顿和取消反应；不先提高上限。
2. 为现有格式加恢复进度与在安全阶段取消；取消要清理本事务暂存，保持原库。
3. 只有实测证明现有格式不足，再设计 manifest + 分块二进制格式；保留 v2 导入，加入每块大小/哈希与总容量预检。
4. 大格式与 STORE-03 共用提交日志，避免开发两套恢复状态机。上限提升必须基于目标设备容量证据。

验收：低内存设备可预测地成功或安全拒绝，用户可取消，失败/取消无半成品发布。回滚：新格式先保持可选；保留 v2 读取与原有 512 MiB 限制，不能通过升限掩盖故障。

### STORE-05 · P2 · 任务摘要跨窗口持久化可能互相覆盖

**证据。** `src/composables/useTaskCenter.ts:31` 的 writeTail 只在当前页面串行，保存时整份 tasks 覆写同一 KV 键；`:56` 的 hydrateTasks 仅在首次成功后读取。窗口 A/B 都完成加载后，各自创建任务，再按 A→B 保存，B 的旧快照可以覆盖 A 的摘要。没有跨窗口合并或锁参与。这是静态可推导的摘要风险，本次未运行两窗口行为复现；不表示底层真实任务一定丢失。置信度中高。

落实步骤：

1. 先补两个独立模块实例共享 KV 的确定性回归，验证创建、更新、清理与重新连接 backend ID 四种交错。
2. 在同源互斥内重新读取并按 task.id/updatedAt 合并，或者改为逐任务记录；clearCompleted 需明确删除意图/修订，防止删除后被旧窗口复活。
3. 通过 BroadcastChannel 或 storage 通知刷新其他窗口摘要；通知是同步辅助，不替代事务。
4. 保持刷新后 interrupted 和用户确认的设计，不把合并摘要直接升级为自动重试模型任务。持久任务恢复继续按 roadmap A05/A06 单独决策。

验收：两个窗口各自产生的摘要都可再次加载，任务删除不复活、backend ID 不重复，未知在途任务不自动重发。回滚：仅回退摘要同步层，不清空用户任务记录或取消真实后端任务。

### STORE-06 · P2 · 入册失败后的清理错误缺乏可追踪状态

**证据。** `src/application/artwork/saveGeneratedArtwork.ts:64` 调用 appendArtwork，`:69` 在失败时发起 deleteImage 并吞掉清理错误；返回值只带原错误。代码注释已说明它不是提交结果不确定时的恢复协议。roadmap `:16` 的“A02 失败与补偿边界”明确保留此事项，本报告复核该既有待办，不重复作为新发现。

落实步骤：

1. 区分保存确定失败、提交结果未知、清理失败三类状态，记录操作 ID、受控 image ID 和独立诊断；不得把图片或提示词全文写入诊断。
2. 确定提交状态前不盲删图片、不自动重试生成；使用稳定作品/操作身份核对实际仓库记录。
3. 清理失败保持可重试的待补偿记录，结合现有引用重扫进行恢复；用户收到“生成成功但尚未入册”的准确说明。
4. 用适配器验证“提交前失败”“提交后响应异常”“删除失败”“重试时已存在”等行为，再连真实 IndexedDB 验证。

验收：用户能分辨生成与保存结果；异常提交不会删掉已发布原图；失败清理可追踪、可重入。回滚：关闭自动补偿分支时保留原图和待办记录，优先可恢复性。
