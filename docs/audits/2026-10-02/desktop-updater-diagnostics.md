Tauri updater 2.13.0 仍把完整包存入内存后校验，不发送 Range，也不持久化部分下载。服务器支持 Range 不代表客户端已续传。本次明确告知取消/失败后重试将重下完整包；未实现新的下载缓存、差分或续传协议。

## 安全续传与吞吐复核（2026-10-02 晚间）

### 可行性与最小实现

本次只修改 updater 命令、其私有模块、updater 取消文案与已有测试、桌面 Cargo 依赖引用及本报告。工作区其他会话的 NSIS、离线助手、资源暂存与业务后端改动未纳入本次工作，未打包、安装、发布或切换更新源。

实际 Cargo.lock 锁定 `tauri-plugin-updater 2.13.0`、`reqwest 0.13.4`。本机锁定库源码及[上游实现](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs)核对结果：

- `Update::download()` 每次新建内存 `Vec`；回调只有 chunk 大小和总长，既不交出原始字节，也不提供响应 ETag、最终 URL 或持久化缓存。没有可开启的安全续传配置。
- 可设置请求头，但只加 Range 会让库把剩余片段当完整安装包验签，不能恢复已下载前缀。
- `Update::install(bytes)` 不再次验签；验签函数是私有的。自行下载后直接调用 install 会绕过原下载路径的签名保护。
- 无需 fork 整个插件。保留其检查和安装入口，新增三个私有小模块：`cache.rs` 管单槽缓存，`download.rs` 管单连接 HTTP 续传，`verify.rs` 按锁定版本保留签名及签署版本语义。续传阶段仅显式引用原锁文件已有的 reqwest、rustls、base64、minisign-verify、semver，没有新增 crate 版本或第三方代理；后续 HTTP/2 对照单独记录依赖变化。插件固定为 `=2.13.0`，升级前需复核验签适配；上游提供公共外部文件验签入口后可删除该适配。

这是单个安装包的顺序下载，没有多线程分片、任务队列、通用下载管理器或下载源自动切换。其收益是保留中断前的有效字节，不声称提高网络吞吐。

### 续传、校验和文件归属

| 边界 | 当次实现 |
| --- | --- |
| 缓存位置 | 当前 OS 用户的 Tauri `app_local_data_dir()/updater-cache-v1/`，固定 `package.part`、`download.json`、`download.lock`；不使用安装目录、资源助手缓存或业务库。跨进程 OS 文件锁防止并写，原有跨窗口会话锁仍保留 |
| 缓存身份 | SHA-256 绑定缓存格式、应用 identifier、当前/目标版本、target、CPU 架构、清单原始 URL、签名、公钥；身份变化直接清空旧槽。该哈希用于命名身份，不能替代安装包签名 |
| 失效条件 | JSON 损坏、超过 16 KiB、身份变化、长度异常、无强 ETag、未知总长、文件超过 7 天未更新时从零开始。缓存最多一个、包体上限 2 GiB；重试时清理失效槽，不遍历或删除其他目录 |
| Range | 仅有有效前缀时请求 `Range: bytes=N-` 和强 ETag 的 `If-Range`，固定 `Accept-Encoding: identity` 并禁用自动解压。`Accept-Ranges` 只作提示，不凭 HEAD 就认定续传成功 |
| 206 | 必须同时匹配起点、末尾、总长、响应体长度（若提供）、强 ETag 和最终资源身份，才追加；弱 ETag 不使用，Last-Modified 不作为降级续传凭据 |
| 200 / 416 / 异常范围 | 200 先截断旧文件再写完整响应；416、错误 206 或编码异常最多执行一次无 Range 的干净重试，再错则失败，不无限重试 |
| 重定向 | 每次从清单原始 URL 请求，沿 HTTPS 重定向重新获取临时授权；仅 GitHub `release-assets.githubusercontent.com/github-production-release-asset/` 的资产路径可忽略临时 query，其他 URL 的 query/path/origin 改变都回退。最终 URL 只存散列，不落盘授权参数 |
| TLS / 代理 | 证书和主机名验证保留，检查与下载均 HTTPS-only（包括重定向）；保持已有系统代理/显式代理语义，不添加代理或关闭验证。测试仅在其私有 loopback client 覆盖 HTTPS-only |
| 完成校验 | 校对传输长度后读取完整包，以原公钥验 minisign 文件签名和 trusted comment 的全局签名；验签后再校对签署版本。沿用当前 `requireSignedVersion` 配置，未擅自改变旧签名兼容政策。即使全部字节来自缓存也必须重验；失败清空缓存并返回明确错误，下次重试全量 |
| 取消 / 超时 | 保留 15 秒连接、45 秒读取空闲、30 秒清单检查超时；不限制持续收到数据的完整包总时长。取消丢弃网络 future，已完成的同步 chunk 写入可供重试。后台完整验签可收尾，但不能在已接受取消后启动安装器 |
| 崩溃 / 清理 | 新身份先持久化失效 metadata，再截断并同步旧包，之后才允许发布新响应 metadata；损坏 JSON 按缓存未命中处理。拒绝缓存及父路径中的链接/reparse point。验签后的同一份内存字节交给安装器；交接前清空自身缓存，Windows 成功启动安装器后由原库退出 |
| 进度 / 速度 | 进度包含已恢复字节；本次速度只计算当前请求实际收到的字节，不能把缓存算成提速。取消提示改为下次尝试续传，失效时重新下载 |

范围与 validator 处理依据 [RFC 9110 的 If-Range 定义](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-range)。未知或不符合条件的服务端采用完整下载回退，优先避免拼接不同资源。

### 当前机器有界网络证据

用户确认慢在下载进度，并反馈「都慢」；本次按应用与浏览器均慢理解，但未取得真实浏览器的数值证据，也未把当前电脑证据当成另一台笔记本测试。

当次线上清单已是 **1.8.1**；固定采样同一版本的 `AI-CG-Studio_1.8.1_x64-setup.exe`，体积 **639,536,640 字节**（约 639.5 MB / 609.9 MiB）。首次报告的 1.7.4/638 MB 是较早时点，不能沿用为当晚现状。

机器/条件：当前 Codex Windows 11 Pro 10.0.22631 x64；2026-10-02 19:02 左右（Asia/Shanghai）；直接复用桌面已编译的 reqwest 0.13.4 + Rustls/ring + system-proxy、相同 updater UA 和超时。额外限定每轮最多 12 秒或 8 MiB。环境无 HTTP(S)/ALL_PROXY，WinHTTP 直连，WinINET ProxyEnable=0、无 PAC URL；不能排除浏览器 WPAD、VPN、路由器或透明网络设备。没有关闭 TLS。

两轮总包体 **491,277 B（0.469 MiB）**，没有完整下载安装包。均为 HTTP/1.1、同一个 release-assets IP；一次 302 后的最终响应提供一致强 ETag `"0x8DF2070804CA4BB"`，范围响应精确从 261,901 字节开始。独立 HEAD 全链 1.783 秒，累计 TLS 0.835 秒；这些是 HTTP 客户端计时，不是浏览器瀑布。

第三轮直接 include 修复后的 `download.rs` / `cache.rs`，相同固定版本 URL、UA、TLS/代理配置，在自己的全新诊断缓存执行实际下载与写盘；12 秒后丢弃 future，重新打开仍保留 **311,053 字节**和强 ETag。三轮总包体 **802,330 B（0.765 MiB）**，没有超过采样上限。最后一轮响应就绪时间包含缓存 metadata 持久化，不能视为纯网络 header 时间；它未单独记录最终 HTTP 版本/IP。前后采样时间不同，21.29 → 25.30 KiB/s **不能证明稳定提速**，更不能冒充已安装客户端的 A/B。

**结论：已在当前机同库探针复现正文低吞吐，连接和重定向不是这两轮慢下载的主要耗时；Range 可通过实际 GitHub 跳转使用。尚不能归因到某个 ISP/CDN，也不能把第二行称为修复后提速。** 两轮短样本不是统计控制实验；当前客户端未编译 HTTP/2，但没有浏览器协商及对照证据，不能据此盲目改协议或加线程。

真实 Edge/Chrome A/B 尚未完成：可用控制仅暴露 Codex 内置浏览器，下载 API 无可保证上限的取消/字节采样接口。本次没有启动可能下载完整安装包的浏览器任务，也没有用 curl 或 headless 新配置冒充用户浏览器。因而尚无「实际安装进程 vs 用户浏览器」或已部署客户端的前后速度对照。

如果在同机同网络的真实浏览器有界对照也慢，下一步应评估**发行方控制的对象存储/CDN**：同一已签名不可变版本资产、HTTPS、自有授权、强 ETag、Range/If-Range 与跨节点一致性必须逐项验收，清单只在资产校验通过后切换。它增加分发费用、密钥与缓存失效运维，不能仅换 URL 就保证快。本次不创建资源、不上传或切源，不接第三方下载代理。若以后取得「只有应用慢」证据，则优先比对实际进程的代理/PAC、TLS/HTTP 协商与连接计时，再选择针对性修复。

### 本机浏览器引擎与 HTTP 协议对照

19:44 在本机现有 Chrome **154.0.8037.95** 的全新隔离 headless context 中补做一次原生 DownloadManager 下载，未读取或修改用户浏览器会话。CDP 在响应头阶段只允许既定版本资产的准确 206、原 ETag、`Content-Range: bytes 0-2097151/639536640` 与 2 MiB Content-Length；最多放行一次正文。达到 2 MiB 立即取消下载并关闭测试 context，另有 12 秒截止；不是 Playwright/Node HTTP 代下，也未运行下载内容。

结果：Chrome 实际协商 **h2**，目标 IP **185.199.110.133**，没有磁盘缓存或 Service Worker 命中。2,097,152 B 用时 **2.724756 秒**，全程 **0.73401 MiB/s**；响应头在 1.508161 秒就绪，正文阶段约 **1.644 MiB/s**。最终 download state 为 canceled，仅一个正文响应，零错误、没有完整 EXE。证据 `browser-probe/report.json` 和忽略的 Chrome NetLog。

它支持用户所述“同机同包浏览器更快”，但仍是隔离 profile 的有界浏览器引擎测试，不能声称操控或复测了用户通常使用的浏览器会话。相较此前 reqwest 样本，时间、TLS 实现及 CDN IP 也不同，因此需用同一 reqwest 仅改变协议再验证。原 updater 关闭 reqwest default-features 后没有启用 `http2`；[reqwest 文档](https://docs.rs/reqwest/0.13.4/reqwest/#optional-features)确认这是独立功能开关。

19:49 使用同一新编译 reqwest 0.13.4、同 UA、同一 TUN/默认代理设置、同 2 MiB Range 请求做 **HTTP/1.1 → 默认 ALPN → HTTP/1.1** 对照。仅诊断 client 固定已观测的 GitHub IP 和 Chrome 命中的 CDN IP 185.199.110.133；保留原 URL/SNI 与证书校验，未修改系统 DNS 或把 IP 写进产品。三轮均校验准确 206、范围、长度、原 ETag，实际接收量各 2 MiB，零超限：

| 同库协议模式 | 总耗时 | 含连接的全程平均 | 正文阶段平均（包含空闲尾部） |
| --- | --- | --- | --- |
| HTTP/1.1 首轮 | 2.887 秒 | 0.693 MiB/s | 1.702 MiB/s |
| 默认 ALPN，实际 HTTP/2 | 1.364 秒 | 1.466 MiB/s | 4.312 MiB/s |
| HTTP/1.1 复核 | 2.441 秒 | 0.819 MiB/s | 1.581 MiB/s |

在这组受控条件的小样本里，H2 正文约为 H1 的 2.53–2.73 倍；它支持保留 HTTP/2 能力的最小客户端改动。另一方面，固定到该 IP 后 H1 本身也显著快于早先约 0.02 MiB/s，**不能把此前全部极慢归因于缺少 HTTP/2**，DNS/CDN 边缘、网络路径和时段也会影响结果。没有声称 638 MB 整包可持续达到这些速度。原始记录 `http2-samples.jsonl`，该组三轮总共仅 6 MiB。
