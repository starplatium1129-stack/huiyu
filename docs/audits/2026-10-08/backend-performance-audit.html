具体发现

P2 · 建议先处理 · 已复现

1. 与作品无关的写入也会使搜索缓存失效

触发：打开作品搜索后保存设置、草稿，或发生实际任务状态写入，再次读取作品搜索。

客户端用整个工作区的 status.revision 判断搜索缓存是否有效；profile 和 task 写入也递增同一个版本。因此即使作品完全未变，也会重新执行全库索引读取、JSON 传输和客户端解析。它会放大第 2 项成本。

证据：本次在全新私有 workspace 调用真实 Storage，索引版本初始为 0；只保存 aics_theme=dark 后，status 和索引版本都变为 1，索引 items 完全相同。客户端当前缓存条件必然不命中。复现使用空作品库证明版本耦合，未测真实页面耗时。

建议：给作品搜索内容使用独立的持久化代次，并随影响搜索的作品变更在同一事务内递增；保留 workspace、writer epoch、恢复/重开身份和跨窗口校验。先做这一局部改动，再评估是否需要改造搜索协议。

定位：artworkRepository.ts:136–145；profile.rs:193；tasks.rs:65；storage/mod.rs:284–297。
P2 · 大库/长文本触发 · 已测量

2. 搜索“索引”仍向客户端发送全库可搜索正文

readArtworkSearchIndex 没有搜索词、结果上限或分页参数。它对每条有效作品读取 story、prompt 等八个字段，拼接并转为小写，全部放入 searchText 返回。借用 SQLite 字符串减少了中间分配，但未改变 O(全部可搜索文本字节) 的扫描、响应和客户端保留规模。

证据：直接编译当前读取函数，1,000 条 × 64 KiB 合成提示文本返回 65,664,024 B（62.62 MiB） JSON；读取函数中位数 61.06 ms。10,000 条 × 512 B 返回 6,400,024 B。序列化、HTTP、浏览器解析及 RSS 不在计时内，不能将这些数字当作页面延迟或峰值内存。

影响：首次搜索和缓存失效后的读取成本随全库正文增长；读取还占用唯一 SQLite worker，期间其它已排队存储操作不能执行。实际排队尾延迟本次未测。

建议：在服务端按搜索词返回有界摘要和游标，保留现有多词子串、Unicode、排序及取消语义。先复用已有行为再选实现；不要直接换成词项搜索而改变匹配结果。

定位：records.rs:42–87；worker.rs:87、240；GlobalSearch.vue:329–337。
P2 · 最近作品热路径 · 已测量

3. 最近 3 条限制了数字候选数，没有限制数据库扫描量

SQL 按 id_key 遍历所有有效作品，从完整 JSON body 提取 timestamp，再在 Rust 中保留数字时间的前 3 条。现有有效记录索引可跳过回收站，但没有提供时间排序；二分插入也没有消除正文解析与全库扫描。

证据：每条 512 B 文本时，1,000 → 10,000 条使中位耗时由 2.43 → 24.80 ms；固定 1,000 条，将文本增至 64 KiB 后变为 30.97 ms，三种数字时间样本都只返回 192 B / 3 条。ISO 字符串时间保留 JS 兼容处理，1,000 条仍全部返回，不能把 candidateLimit=3 当作整个响应的硬上限。

建议：先为常见的数字时间维护轻量、可索引排序字段，避免每次解析正文；历史字符串时间采用单独、明确的兼容路径。保留数值不截断、稳定同分排序、软删和两阶段读取修订核对，不为限量而丢弃旧作品。

定位：recent.rs:14–50；artworkRepository.ts:103–112。

已核实、应保留的优化

  • 目录投影与筛选缓存：使用文件身份和版本失效；旧请求不能覆盖新代次。缓存命中、跨连接写入、导入、预览不提交、权威库缺失等现有行为测试本次通过。
  • 分页和分配：单类型查询使用等值条件，newest 索引与排序相匹配；作品读路径借用 SQLite 文本、移动已解码 Value，确实减少复制。没有重新测量历史报告中的“提速百分比”。
  • 媒体与大结果：媒体校验移出 SQLite worker，冷哈希和暖身份检查分别限流；缩略图同图合并、有界解码；大 WebUI 解码的许可保留到真实任务结束。此项为当前源码审查结论，本次未重跑这些专项。
  • 上游与资源：本机 reqwest Client 复用连接；Comfy history 有退避与终态唤醒；资源同组读取有合并与内存许可。未用省略哈希、路径检查或取消排空换取性能。
