P1数据可靠性已复现

01 · “备份未保存的修改”不能完整导回

导出内容同时包含 changes 和 editor；导入只接收非空的 changes，不恢复 editor。因此，仅编辑了当前记录、尚未暂存时，导出的草稿结构会被拒绝；如果已有暂存变更，当前未暂存编辑仍不会被导回。

复现
在“内容维护 → 批量整理 → 直接填写修改数据”输入与当前导出结构一致的本地合成草稿：{changes: [], editor: {...}}，点击“读取这些修改”，出现“每条修改需要 kind、id、expectedRevision”。本次未向内容库提交数据。
建议
为维护草稿定义明确的格式与版本，导入时同时恢复待保存变更、当前编辑和原版本信息。恢复到编辑态，继续保留冲突检查；也可在导出前明确暂存，但不能悄悄丢掉编辑内容。
验收
“仅有当前编辑”与“暂存变更 + 当前编辑”两种草稿导出后均能恢复原内容；恢复过程不直接写入服务器。

02 · 分屏宽度下，调参和生成分离

在 960 × 720 CSS 像素视口中，参数区排在画布下方，生成条仍属于画布列。滚动到参数区后，生成条随父容器离开视口；此宽度的区块快捷导航也被隐藏。

证据
深色模式、页面滚动 820px 时，生成条顶部为 −113px、底部为 −16.25px，参数区顶部为 −0.25px。浅色模式先前亦观察到同一布局问题；1280 × 800 的三栏布局中生成条可见。
建议
小于三栏断点时，把唯一的生成操作条放入覆盖整个编辑区的滚动容器，或固定在窗口底部并预留空间。避免同时复制多个生成按钮和状态。

P2可靠性 · 浏览器端代码确认

03 · 保存失败应持续可见，并提供补救动作

浏览器绘制草稿写入失败后只调用 flash(...)；默认提示约 2.5 秒后消失。saveFailed 是 composable 内部变量，未返回给界面，用户之后看不到持续的失败状态。

边界
这是浏览器草稿链的问题。桌面端已有 RuntimeConnectionNotice 的持续告警与重试，不能据此声称桌面端也缺少保护。本次未制造配额耗尽或磁盘错误。
建议
暴露“保存中／已保存／保存失败”状态；失败时常驻显示“重试保存”和“导出当前草稿”，直到恢复成功。刷新前仍有未保存内容时给出明确保护。
验收
修复时在已有草稿用例中模拟一次存储写入失败，确认提示持续、当前编辑保留、重试后状态恢复，避免新增重复测试体系。

04 · 把作品备份放到用户会寻找的位置

05 · 普通主导航不宜隐藏 Tab 路径

验收
仅用 Tab、Shift+Tab、Enter 就能依次进入全部主页面，焦点可见；移动到“更多”后的 Escape 回焦行为继续保留。

06 · 任务分页没有转化为前端按需加载

首次连接或运行时代次变化后，前端从 revision 0 开始，每次 100 条循环拉取所有历史，完成后才整体发布。状态层持有全部任务；发生有效更新时，展示 computed 会深拷贝全部记录，列表再逐项渲染。

已有优化
空闲增量轮询不会无故重复克隆，服务端也已有分页；本问题针对首次全量历史及“至少一条任务变化”的路径，不能说每轮轮询都全量拉取。
建议
先读取所有活动／待确认任务与有限的近期摘要，历史记录按需分页；展开任务时再读大输入、checkpoint 和结果详情。保留不可变边界、稳定请求身份和跨页一致性，不能简单截断活动任务来限量。
验收
实施时用隔离历史夹具测首次可交互时间、单次任务更新成本与 DOM 数量；本次未给出未经测量的卡顿或内存数字。

07 · 显式限定 Vite 的依赖扫描入口

本次运行 npm run dev -- --host 127.0.0.1 --port 5173 --strictPort 后，Vite 报 Failed to run dependency scan. Skipping dependency pre-bundling.，错误来源是 runtime/telegram-uiux-research-20261003/ 中的外部研究代码。

原因
配置只把 runtime/** 排除在文件监视之外，没有限定 optimizeDeps.entries。监视排除不等于依赖扫描排除。
建议
把依赖扫描限定为应用的真实 HTML 入口，必要时排除 runtime、archive 和其他产物。无需安装这些研究仓库的依赖，也无需删除研究资料。
验收
修复后冷启动一次，日志不再扫描研究目录，应用入口正常打开。本次页面仍可打开，故不将其描述成整个产品无法运行；这也不是生产包故障证据。
