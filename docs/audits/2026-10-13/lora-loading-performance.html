LoRA 切换优化与冷加载定位

2026-10-13。本轮落实两处传输优化：融合底模恢复的读取与上传重叠，以及兼容 LoRA 热切换的逐 adapter 打包上传；同时补齐初次 LoRA 装载和融合恢复的独立观测。修改 5 个 Python 模块与 1 个 Rust 模块，无新增依赖。实际提速、内存峰值和图像结果尚未做设备验收。

链路本轮改动收益依据与代价
融合底模恢复compiled-fused-sage 切换 LoRA、强度或卸载时，同 dtype 的 CUDA 源文件恢复使用两个至多 16 MiB 的槽位。读取下一块时，上一块异步复制到 GPU；复用槽位前等待对应 Event。移除大体量恢复中逐块读取与上传的串行等待。总活跃读取／转换张量仍不超过 32 MiB；不是整个进程 RAM 或文件缓存上限。分块变小也会增加复制和 lease 检查次数，净收益需实测。
普通 LoRA 热切换完整组预检通过后，按每个 adapter 的实际 CUDA 目标设备复用现有打包上传器，再交给原 Diffusers／PEFT 完成交换或 compiled copy。每个 adapter 完成后立即清理交换回来的旧权重引用。适用 pinned 路径把多次小张量上传合并为至多 32 MiB 的 DMA 窗口。两个 host 暂存槽合计至多 64 MiB；另有约一份 adapter 加对齐空间的新 GPU flat 与旧权重共存，低显存余量设备可能更早 OOM。
冷加载与切换定位新增当次 nativeRuntime.loraLoading 与 fusionRestore，贯通 Python 采集、worker 回执与 Rust 白名单。移除配置推导中未被固定 Diffusers 版本使用的全模型 state_dict 构造。可分别看到初次／回退 LoRA 装载、兼容热切换、打包传输与融合恢复，避免只依赖总模型获取耗时。移除 state_dict 遍历是附带收益，不宣称它是冷加载主瓶颈。

冷加载检查结论

现有底模链路已将依赖导入与完整哈希并行，并按组件顺序反序列化、上传、释放 CPU 引用。Rust worker 在兼容 LoRA 切换时也已复用。源码检查未发现值得再做一次同类缓存的重复冷启动；完整权重校验和反序列化仍是较大开销，当前没有新的分阶段设备数据可以量化其占比。

本轮保留逐组件装载的内存边界。初次 LoRA 装载仅增加耗时记录，保留原 metadata、初始化器及 dtype／设备转换流程；打包优化只进入完成全部预检的兼容热切换。继续并行加载组件会增加 CPU 权重共存量，且固定依赖的装载上下文存在共享状态，因此未直接并发调用这些加载器。

正确性与观测边界

源文件恢复仍先校验完整目标集合，并在读取和复制边界核对文件 lease；不通过减去 BF16 LoRA 增量恢复底模。双缓冲仅用于大于 16 MiB、每行不超过 16 MiB 的同 dtype CUDA 组。CPU、需转换 dtype、小组和大行保持原串行路径。按完整 CUDA device 分组；正常结束及异常都先等待实际复制流，再释放缓冲和 pinned 缓存，包括复制已经入队但 Event 记录失败的情况。

热切换保留全部格式、键、有限值、shape、dtype 与 PEFT 配置兼容检查。CPU 目标和上传器不适用布局继续走原 PEFT tensor.to；真实上传或交换错误向上传播并清空驻留模型，不在部分修改后静默回退。原模型和 LoRA 文件不写入，数值计算配方与 TeaCache 作用域不变；源码保持值的语义不等于已证明设备输出相同。

loraLoading.uploads 仅记录成功的打包上传。CPU／不适用布局无逐设备条目，其原 PEFT 上传耗时包含在 LoRA 总 wall 区间。fusionRestore.sourceBytes 是完成恢复的源字节，snapshotBytes 是保留的独立 CPU 快照体量；复制次数及流水／串行组数只统计源文件恢复，不含快照复制。所有新增记录来自当次 pipeline；无相关操作时不复用旧记录。计时区间包含或重叠于模型获取区间，不能相加，也没有仅为观测新增 CUDA 同步。
