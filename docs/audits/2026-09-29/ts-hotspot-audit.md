## 结论

存在可优化的主线程工作：全局搜索全库读取/索引重建、手绘遮罩的全图快照与空图扫描。但目前没有证据证明必须换成 C#，也没有 C#/Rust 对照实现可用于宣称迁移收益。优先减少搬运和重复计算；桌面搜索适合评估下沉现有 Rust/SQLite 查询。粒子持续渲染值得完整 profiling，但纯物理循环本次测量不足以支持语言迁移。

## 发现

### 1. 全局搜索随作品库规模增长（优先）

`src/components/GlobalSearch.vue:310` 每次打开调用 `readHistory()`，然后 `indexArtworkSearch()`。桌面 `src/platform/desktop/artworkRepository.ts:24` 逐页顺序读取全部记录（每页 200），排序并深复制；在线读取没有复用已加载列表。1 万条对应约 50 个分页请求，前端索引又排序并建立日期显示和完整 prompt 检索字符串。最终仅展示 5 条作品，但 `filter(...).slice(0, 5)` 仍扫描全部候选；匹配函数逐条重复拆查询、转小写。

本次隔离合成 1 万条、每条 prompt 2035 字符：索引重建各轮中位 **21.0–27.6 ms**。原筛选回放使用错误转义的 `/\\s+/`，未按空白拆分查询；**12.5–13.0 ms 仅保留为错误回放记录，撤回其作为实际多词筛选耗时的结论**。没有包含 HTTP、仓库排序/深复制、DOM 更新和绘制，不能当作完整搜索时延，也不能当作用户当前库的测量。

建议：先避免查询内重复正规化与无必要的全量扫描；评估缓存的失效边界。桌面进一步提供受权限/版本约束的后端搜索，只返回匹配摘要和必要分页，保留多词子串匹配、排序与删除过滤语义。该方案利用现有 Rust；仅把同一全量算法翻译到 C#、继续搬运所有记录，不能消除数据链路成本。

### 2. 遮罩撤销与空图扫描（中等优先）

`src/components/inpaint/useInpaintMaskCanvas.ts:51` 每次落笔前同步 `getImageData()` 全图保存，最多 20 份；`:170` 导出前全图读回并用逐字节 `.some()` 检测空图。全空图必须遍历所有字节。

已核对实际入口 `useInpaintImageSource` 使用 `inpaintCanvasSize()`：正常图像尺寸已收敛，不能把 4K 原图直接按 4K 撤销栈估算。1536×1152 输入对应 1216×912 遮罩；4096×4096 输入对应 1168×1168 遮罩。

| 遮罩像素尺寸 | 落笔快照及绘制，各轮中位 | 空图导出检查，三轮 | 20 份 ImageData 字节合计 |
| --- | --- | --- | --- |
| 1216×912 | 1.8–1.9 ms | 31.0–32.7 ms | 88,719,360（84.61 MiB） |
| 1168×1168 | 2.1–2.5 ms | 39.0–40.4 ms | 109,137,920（104.08 MiB） |

字节合计是实际数组 payload，不是进程内存或泄漏证据；不含 Canvas backing store、驱动与 GC 暂留。空图检查是提交时发生的一次操作，不是每帧。默认遮罩模式为自动，手绘时才走此链路。

建议：优先局部撤销数据、快照总字节预算、减少空图扫描范围，并确保擦除/撤销后空图判断仍正确。若迁到 C# 却保留全幅读回和 IPC 传输，可能新增复制成本；需要把数据所有权和处理一起规划，不能只换扫描函数。

### 3. 粒子模拟是高频工作，但尚未证实为主要瓶颈

`SemanticParticleField.vue:308` 在 JS 中逐点模拟，`:410` 每帧调用；完整模式依显示器 rAF 运行，hero/ambient 即使主体稳定仍有碎屑绘制，只有 backdrop 稳定时停循环。`particleDensity.ts` 允许参考尺寸粒子场达到 48,000 点。`particleGpu.ts` 已用 WebGL2 实例化绘制，但每帧仍在 JS 中整理顶点、边界并上传。

直接提取当前 `simulateParticles()` 函数，用合成分布和活动指针测量：8,000 点各轮中位 **0.06–0.09 ms/次**；48,000 点 **0.420–0.425 ms/次**。这是预热后批次均摊 CPU 时间，未包括顶点整理、WebGL 提交、GPU、Canvas 合成、真实点云与页面竞争，不代表 FPS 或单帧尾延迟。

建议：先记录完整帧调用栈及 GPU/合成成本，再决定 Worker、GPU 模拟或原生整体渲染。当前纯模拟结果不支持优先引入 C#；跨进程逐帧传递粒子坐标还可能增加开销。

## 已核对的排除项

- 桌面 Live2D 已由 Rust overlay + Cubism Native 执行模型帧循环，不能将其纹理、遮罩和物理成本归因于 TS。浏览器后端属于另一条路径。
- 原生口型/情绪已有 latest-intent 合并、去重与 16/50 ms 间隔。前端仍运行情绪时钟，但本次没有测得它是瓶颈。
- 图库已有查询索引缓存、排序缓存、Set 项目成员查询及分页渲染；不能重复把先前已修复的问题列为现状。
- 聊天草稿/音量已分键保存，流式会话保存调用经核查不是每 token 全库序列化；未开展聊天大历史压力测试。
- 液态玻璃像素计算已有最长边 360、缓存、串行队列、每 8 行让出执行及可见性限制；未将存在循环本身当作迁移理由。
