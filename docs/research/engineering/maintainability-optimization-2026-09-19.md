## 1. 结论：下一步应减少“改一个功能需要理解多少地方”

当前 HUIYU 已具备 TypeScript 源码与构建链、页面与 composable 分层、作品仓储、统一 API 客户端、质量套件、工作流注册和交付证据机制。最新一批还完成了统一词条、随机配置快照、任务阶段规范、配方恢复兼容检查，以及图库和语音生命周期修复。因此，不建议再次启动“全站架构重写”“全面迁移 TypeScript”或“从零建立测试体系”。这些说法会忽略已经完成的工作。[S02] [S03] [S04] [S11] [S12]

**本轮更有价值的方向，是在现有架构内收紧数据与模块边界，让后续小功能更容易找到入口、更少依赖隐含约定、更容易证明没有回归。**

建议先处理三类问题：文档与源码职责的漂移；作品历史和 API 返回值的类型可信度；测试对具体源码写法的过度绑定。模块依赖、资源生命周期、CI 成本和第三方适配则在此基础上逐步治理，不为目录整齐或抽象程度而重构。

本审查没有建立新的运行时 P0 缺陷结论，也没有测得新的性能瓶颈。下面的 P1/P2 是本专题内的建议优先级，**不替代 `docs/roadmap.md` 的正式执行顺序**；采纳后的任务只在 roadmap 维护进度，本文件保留审查依据。

### 审查范围与证据限制

本次定向阅读了协作规则、项目状态与规划、维护和 TypeScript 指南、工作流、ESLint、质量流水线与部分测试源码，以及作品类型、历史 store、工作台 store、生成 API、PhotoSwipe 适配组件、语音 composable 和服务配置源码。链接均固定到上述提交，避免 `main` 后续变化使依据漂移。

**本次未修改仓库、未提交或推送，未运行 npm 安装、类型检查、测试、构建或实际应用。** 没有完成全仓依赖图、复杂度、全部重复代码或 CI 耗时统计；没有运行真实模型、语音设备、Windows/Tauri、GPU 或安装验收。既有报告中的通过结果只作为当时证据，不记作本次重新验证。[S01] [S03]

## 4. 优先处理的五项

### M01 — 文档状态只保留一个权威入口

**已核实的现状。** `docs/INDEX.md` 仍将 009 描述为“F0–F7 待执行”，将 010 描述为“C0–C7 待执行”；但 roadmap 已写明 009 办公机阶段完成，010 办公机已接线、设备待验。`docs/maintenance.md` 的角色蓝图维护说明仍保留“UI 保存只写聚合、可能被旧分片覆盖”的旧结论，而当前状态与规划已经登记保存事务和持久化工程完成。[S20] [S02] [S18] [S21]

这不是排版问题。后续维护者或代码代理可能根据旧入口重复改造已完成的保存链，或者将“设备待验”误解成“功能尚未开发”。

**建议改法。** 索引只描述文档用途和链接，不重复复制动态阶段状态。`project-status.md` 维护当前实现与验证边界，roadmap 维护剩余任务；专题记录保留日期与历史状态。维护手册中的旧风险应替换为当前入口与仍然有效的限制，历史原因改为链接，不抹除历史失败证据。009、010 的表述必须区分“代码实现”“办公机验证”“设备/模型/安装验收”，不能只写一个笼统的“完成”。

**验收与回退。** 从 INDEX、maintenance、project-status、roadmap 任一入口进入，都不再得到互相冲突的当前结论；仍待真实设备验证的事项保持开放。运行现有 `docs:check` 验证链接，但语义一致性需人工核对，不能认为链接通过就证明状态正确。本项仅改说明和索引，可独立回退，不与运行时代码混合提交。

### M02 — 文档明确区分 `.ts` 源码与 `.js` 运行文件

**已核实的现状。** TypeScript 指南已经明确：网关、路由、维护脚本和测试以 `.ts/.mts/.cts` 为源码，`.js/.mjs/.cjs` 是构建产物，不能直接修改。维护手册的“是否手动编辑”表却仍将 `server.js`、`server/config.js`、`routes/*.js` 等作为需要修改的文件。实际仓库存在 `server/config.ts` 源码。[S04] [S18] [S22]

**建议改法。** 将文件职责表拆成“编辑入口”和“执行入口”两列。例如配置逻辑改 `server/config.ts`，运行时仍使用构建后的对应模块；维护脚本改 TypeScript 源文件，而 `npm run wf -- …` 和现有 Node 命令继续执行生成文件。不要全局把命令中的 `.js` 替换为 `.ts`，否则会破坏当前兼容入口。

源码与产物对应关系优先复用现有构建器和 TypeScript 指南；不另维护一份覆盖全仓、需要人工同步的文件清单。对重点维护入口，可在职责表注明“生成文件，禁止手改”，并链接具体源文件。工作流说明继续以 `scripts/workflow.ts` 为命令注册源，而不是建立第二份注册表。[S04] [S17]

**验收与回退。** 按维护手册完成一次隔离的配置或路由修改时，维护者无需猜测应改哪个扩展名；修改源码后产物由既有构建生成，重新构建不会丢失修改。纯文档修正不需要为了证明路径关系执行安装或部署。不要借本项搬迁所有编译输出目录。

### M03 — 先修作品历史的类型断层，不做全站类型重写

**已核实的现状。** `ArtworkRecord.id` 允许 `string | number`，字段整体兼容旧记录；`usePromptHistoryStore` 却把 `history` 声明为 `ref<unknown[]>([])`，载入后写入 `parseArtworkRecords(raw)`。工作台 store 再把它双重断言为 `Ref<HistoryEntry[]>`，而 `HistoryEntry.id` 仍声明为 `number`，且假设更多字段完整存在。[S07] [S08] [S09]

以下是两个不同模块的源码摘录，用于展示连接方式，不是建议新增的实现：

```ts
// src/stores/promptHistoryStore.ts
const history = ref<unknown[]>([])
```

```ts
// src/stores/promptBuilderStore.ts
const history = _historyRef as unknown as Ref<HistoryEntry[]>
// ArtworkRecord.id: string | number
// HistoryEntry.id: number
```

当前记录解析器主要检查记录对象与 ID，并不验证 `HistoryEntry` 所有必填字段。双重断言没有补上运行时保证。最新实现已经处理过字符串作品 ID 的恢复，因此这项应该被理解为**让声明追上已有兼容行为**，不是断言该功能仍未修复。[S03] [S09]

**建议改法。** 先让历史 store 表达它实际保存的 `ArtworkRecord[]`，再梳理工作台、历史恢复、作品册需要的最小字段。需要完整生成配方的入口通过显式解析/适配获得可信结构；只负责浏览旧作品的入口继续允许字段缺失。共同类型优先归入现有纯类型域，旧 store 导出可保留兼容转导出，不要求所有调用方同批迁移。

不要将所有旧数据强行补成“完整配方”，不要为满足类型而把缺失的引擎、种子或模型参数猜成默认值。保留未知扩展字段和原始 ID；不得顺手将字符串 ID 转成数字、改写存储键或改变现有对象匹配语义。TypeScript 的类型收窄应来自可证明的检查，而不是再叠一层断言。[T02]

**验收与回退。** 覆盖数字/字符串 ID、旧记录缺字段、合法零值、项目与收藏、软删恢复，以及 Remix/配方检查。工作台历史连接不再依赖上述双重断言；非法的完整配方不能被静态类型静默接受，缺字段的旧作品仍可浏览并明确提示缺失。先改解析和类型、保留旧接口，再迁移消费者；不启动用户库迁移，回退不需要恢复数据。

### M04 — 让生成 API 的返回类型与实际校验强度一致

**已核实的现状。** `src/api/generationApi.ts` 声明了完整的 `GenerationStatus`、`GenerationJob` 和信封类型，但局部 `isStatus` 只检查 `online` 与两个数组，`isJobEnvelope` 主要检查 `job` 是对象且 `job.id` 为字符串。`status`、`provider` 等声明字段并没有在这个 validator 中逐项核实。[S10]

这不意味着统一客户端没有错误处理或通用信封保护，也不构成已经发生运行故障的证明。维护风险在于：后续消费者看到一个完整返回类型，可能误以为业务字段已经全部验证。

**建议改法。** 从 `getJob` 这一条窄链开始，明确“原始响应 → 校验/兼容映射 → 页面使用的数据”三层。复用已有生成阶段、进度与引擎能力规则，避免前端、路由和测试各自维护一份近似枚举。无法识别的阶段和未知进度继续明确处理，不能改回按文案猜状态或将未知进度伪装为 0%。[S03] [S10] [S25]

优先使用现有解析函数、类型守卫及已有契约工具。仓库已经使用 Ajv 依赖；是否把某个边界转为 schema，应取决于是否减少重复定义，不默认再增加另一套全站校验框架。HTTP 传输结构、归一后的 UI 状态、持久化记录和不同引擎请求可以不同，不应为“统一”强行合成一个巨型类型。[S11]

**验收与回退。** 用隔离响应覆盖缺少/非法 `status`、错误 `provider`、未知阶段、`null` 进度、错误信封，以及当前服务的合法响应；保证取消和超时语义不变。二进制结果下载保留现有独立边界。先完成单端点解析与测试，再推广；若出现兼容缺口，回退该解析适配层，不回退整套 API 客户端。

### M05 — 减少“行为没变，测试却因写法变化而失败”

**已核实的现状。** `test-page-architecture.ts` 使用源字符串和正则判断路由懒加载、文件存在、`<h1>`、组件接入及样式归属。部分约束已经为抽到子组件的实现添加特殊分支。最新实施审计也记录了语音契约中的旧源码精确匹配断言需要修正，并明确其验证是累计证据，不是一次完整门禁总 PASS。[S14] [S03]

**建议改法。** 将断言分成三种职责：用户行为通过 Vitest 组件/逻辑测试或 Playwright 验证；导入关系、懒加载、目录边界等静态约束尽量通过结构解析验证；保护字段字节基线、CSP 和已确认必要的源码策略继续严格保留。不能将“减少脆弱测试”理解为删除安全门禁或放宽定稿内容保护。

先迁移最近反复需要修补的断言，不全量重写测试。例如“取消后迟到回调不得写入新会话”应通过可控制的 Promise/事件夹具验证，而不是只搜索源码是否出现某个变量名。可访问标题与焦点等面向用户的行为由渲染结果验证；Playwright 官方也建议围绕用户可见行为和测试隔离组织用例。[T03]

**验收与回退。** 纯重命名内部函数或提取等价 helper 时，行为用例仍通过；有意移除取消/身份守卫时，对应回归用例必须失败。每移除一条旧断言，先说明它保护的风险由哪条新用例覆盖。避免“先删旧断言、以后补测试”；恢复旧测试不应要求回退业务功能。

## 5. 在上述基础上推进的五项

### M06 — 约束依赖方向，比再建一层目录更重要

**已核实的切入点。** 当前协作规范要求复杂状态下沉，ESLint 已区分浏览器与 Node 环境。阅读到的 ESLint 配置未配置 `no-restricted-imports`；已有页面架构测试更多关注入口、文件和样式。工作台 store 同时导出业务类型、提示词映射常量与 Pinia 状态，是值得进一步核对调用关系的边界。[S01] [S07] [S14] [S23]

**这里没有完成全仓依赖扫描，不能据此宣称已存在循环依赖或严重分包污染。**

**建议改法。** 先选“作品历史”和“提示词工作台”两个域，记录公开入口、内部实现、数据写入方、异步任务拥有者和对应测试。先绘制真实导入关系，区分运行时导入与 `import type`；需要跨域调用时，优先通过已有仓储、API 或窄接口，而不是访问另一模块内部状态。

新增约束以少量高价值规则起步：纯类型/纯计算模块不依赖 View、Pinia 实例或浏览器单例；底层存储不反向依赖页面；非适配模块不直接消费第三方查看器实例。若某个纯常量确实因导入 store 而带入运行时依赖，再移动该常量；不要在没有调用证据时批量搬家。

可先使用现有 ESLint 的静态导入限制能力，但 `no-restricted-imports` 不覆盖动态 `import()`，CommonJS `require()` 也需要单独处理。别把一个规则的通过当作完整依赖图证明；需要时再扩展已有架构检查，并验证别名、相对路径和合法类型导入。[T01]

**验收与回退。** 为允许/禁止的导入各提供夹具；新增代码无法绕过试点边界。旧兼容入口先保留，逐步迁移消费者；不引入庞大的全站 `index.ts` 导出桶，也不要求从横向目录整体迁往另一种架构。相同职责、相同依赖和相同测试边界都没减少时，不为了文件更小继续拆分。

### M07 — 把生命周期修复沉淀成可复用的责任约定

**已核实的现状。** PhotoSwipe 适配组件已有 `revision`、`dispose()`、解码集合、URL 回收与 ResizeObserver 清理；语音 composable 已有 session、AbortController、预热/状态代际和取消播放句柄。Live2D 工程契约也明确保留唯一销毁入口与既有顺序。因此，本项不是补做“尚不存在的清理”，而是降低未来再次写错的概率。[S15] [S16] [S19]

**建议改法。** 先给现有模块明确资源所有权，不立刻创造一个覆盖图片、音频、网络、原生模型的万能生命周期框架。

| 范围 | 责任应如何固定 | 不能顺手改变的语义 |
| --- | --- | --- |
| 观画组件 | 查看器实例、Observer、解码任务和自身创建的 Blob URL 由适配组件收尾 | Gallery 继续拥有外层 dialog、焦点和业务操作；只有 URL 拥有者负责回收 |
| 语音会话 | session 内的翻译、预热、播放等待与口型帧循环有明确停止者 | 停止当前轮次、切换角色、销毁能力不是同一个操作 |
| KeepAlive 页面 | 区分可见、激活、停用与真正卸载 | 隐藏暂停不自动等于清空需要保留的草稿或缓存 |
| Live2D 双后端 | 继续走既有 runtime 销毁与能力分支 | 不复制第二个销毁器，不改变 Pixi-first 等既有契约 |

先复用测试夹具：延迟完成、失败分支、重复释放、部分初始化失败、A→B→A 切换、卸载后回调。只有当多处确实共享相同语义时，才提取很小的取消/代际 helper；销毁顺序和业务缓存仍由各模块决定。

**验收与回退。** 旧会话结果不能覆盖新会话；等待 Promise 能结束；重复清理安全；同一资源没有互相竞争的释放者。DOM/Blob URL 趋势测试继续保留，但不因此宣称 GPU、纹理或进程内存已通过真机验证。一次只迁移一个使用点，出现差异可回到原有局部实现。

### M08 — 先让门禁易定位，再决定哪些计算值得去重

**已核实的现状。** `quality-test-inventory.ts` 已有集中清单；执行器已输出摘要、失败摘录和耗时，check/contract 默认采用 180 秒超时，unit 为 300 秒。`package.json` 保留多种单项和 E2E 入口。Quality 流水线中的 checks、contract、e2e 都执行构建，且各 job 使用隔离 checkout；contract 的注释明确说明需要真实 SPA 产物。[S11] [S12] [S13] [S24]

因此，不能简单断言“仓库没有统一测试入口”或“三次 build 都是无意义重复”。

**建议改法。** 在现有测试清单上逐步补充明确需要的元数据，例如域、运行环境、并行安全性、单文件超时和隔离资源；保留现有 CLI 与 E2E 分层检查，不再新增一个调度框架。慢契约优先定位启动、等待、清理和外层超时之间的关系，必要时按已确认边界拆分，不统一加大所有超时。

把失败摘要与现有 `docs/evidence/`、交付审计接起来，使维护者能区分：断言失败、类型/构建失败、外层超时、环境缺失、未运行、跳过、定向复验。已有通过数不能把失败入口自动升级为“完整 PASS”。既有证据格式先复用，缺少机器可读字段时再做向后兼容扩展。[S03] [S17]

CI 去重先记录实际耗时、缓存命中、上传下载体积和总墙钟时间。只有收益明确时，再试验由可信的同次运行共享构建产物；必须绑定源码 SHA、锁文件、构建配置与产物哈希，不能将不匹配的产物用于契约或 E2E。现有 TypeScript 构建缓存已经存在，不将缓存从零建设再次立项。[S04]

**验收与回退。** 原有门禁覆盖不减少，单项命令继续可用；失败可以定位到具体测试/阶段，未跑保持未跑。没有测量前不承诺“提速百分比”。CI 试验与业务修改分开，失败时恢复原来各 job 独立构建路径。

### M09 — 第三方能力放在适配边界内，保留明确退出条件

**已核实的现状。** PhotoSwipe 固定为 5.4.4，已有独立适配组件，关闭其内部焦点/键盘控制，将相关责任交给 Gallery；原默认查看器保留，可退出试验。许可文件、锁定版本、模拟浏览器和设备验收边界也已经有记录。[S03] [S15]

**建议改法。** 继续沿用这个薄适配层，不让作品收藏、删除、Remix、配方和任务中心直接依赖 PhotoSwipe 类型或实例。适配层只处理查看器数据转换、尺寸与资源、索引/选中映射、错误、缩放和关闭；作品身份和业务命令由现有作品域负责。第三方内部使用索引不必禁止，但业务操作必须继续绑定稳定作品身份。

在现有研究/实施记录补充简短的“适配契约与退出条件”：允许从哪里引用依赖、默认回退是什么、升级需跑哪些真实库与模拟用例、何种设备证据才支持正式替换、撤回时应删哪些接线。已有许可证和依赖审计继续复用，不重复建立另一份许可证账本。

本项不要求现在把约百行的适配组件再次机械拆开，也不要求给每个库套一层抽象。只有外部接口开始泄漏进业务，或实际升级产生重复修改时，才扩大边界。语音/Live2D 的第三方适配沿同样原则评估，不合成一个万能“引擎插件系统”。

**验收与回退。** 默认查看器继续工作；失败能回退；键盘、焦点、滚动锁只存在一个明确拥有者；关闭与重开不接收旧请求回写。模拟与真实库接入测试职责分开，触屏和 Tauri 仍按 roadmap 真机验收；没有这些证据不将试验默认化。[S02]

### M10 — 让静态规则和工具链声明更容易理解

**已核实的现状。** ESLint 全局忽略了多类生成的 `.js` 文件，但后续仍保留针对其中一些相同路径的“纯 JS no-undef”配置和历史环境分离说明。全局已忽略的目标不会因为后续规则块而重新进入 lint；这部分配置至少需要重新核对有效作用范围。文件长度预警仍为 1000 行，而独立预算门禁是 600 有效行，注释还保留旧单体案例。[S23] [S06]

另一个需要明确的事实是：`package.json` 声明 Node `>=22.18`，`.nvmrc` 与阅读到的 Quality 工作流固定为 `24.18.0`，`@types/node` 为 `^26.1.1`。这些数值本身不证明不兼容；但最低支持运行时、开发/CI 运行时和声明类型来源是不同概念，应有清楚的验证责任。[S11] [S24] [S26]

**建议改法。** 用实际配置展开与小夹具核实 ESLint 规则作用范围，清理失效说明或冗余块，保留生成文件不作为源码 lint 的原则。600 行硬门禁继续保持；1000 行历史预警是否仍有意义应明确，不为了统一数字而降低现有质量要求，也不通过压行规避预算。

工具链先确认项目真正承诺的最低 Node 版本，以及桌面包内实际使用的版本。若继续支持 22.18，则补充针对最低版本的安装/构建启动或相关 API 烟雾验证；若只支持其他版本，须独立评估后再修改声明，而不是本轮静默抬高。对于 Node 类型，优先验证是否存在依赖较新 API 的使用，再选择匹配的类型版本或约束，不能仅凭主版本差异直接降级依赖。

**验收与回退。** 每条关键环境规则有一个会失败的错误示例；维护者能说清源文件由 ESLint 还是 tsc 校验，生成文件由哪条产物门禁保护。工具链变更与业务改动分开；保留锁文件和原 CI 配置可回退，不自动升级全套依赖。

## 6. 实施顺序：按风险拆分，而不是一次做完十项

以下为建议拆分，不是对 roadmap 的直接改写，也不意味着这些批次已经开始。

| 批次 | 范围 | 合入条件 | 不应混入 |
| --- | --- | --- | --- |
| A：维护入口校准 | M01、M02；M10 中确认无行为变化的说明修正 | 文档状态一致，源码/产物职责清晰，现有链接检查通过 | 运行时重构、依赖升级、部署 |
| B：历史类型边界 | M03，并补齐对应行为回归 | 旧作品继续可读，字符串/数字 ID 和缺字段契约成立，类型不再双重断言越界 | 存储迁移、ID 重编码、备份格式修改 |
| C：生成 API 窄切片 | M04；M05 优先覆盖该链路 | 当前合法响应兼容，异常/未知字段行为明确，取消与阶段语义不变 | 三引擎统一重写、生成参数调整 |
| D：可重构性试点 | M05 剩余高摩擦用例、M06 两个域、M07 一个模块 | 行为测试覆盖原风险，依赖规则有正反夹具，生命周期不变 | 全站目录迁移、万能框架 |
| E：工具和适配治理 | M08、M09、M10 余项 | 有实际成本/兼容证据；默认与回退路径都可用 | 无测量的提速承诺、默认替换试验库 |

**建议最先执行 A，再做 B。** 这两批能直接减少后续维护误判，不需要等 GPU、模型或触屏测试才能完成各自的静态/隔离范围。它们通过后，也不能据此关闭原有主力机验收项。

### 每次改动的最小交付记录

记录“改动的唯一目的、受控文件、保持不变的契约、当次验证命令与结果、回退方式”。优先复用现有交付证据格式；不为每个小改动新建长报告。失败、未运行、环境受限和设备待验应独立记录，不能用累计测试数量覆盖状态差异。[S01] [S17]

分支、提交与推送继续遵守当前协作流程和用户当次授权；本文件本身不授权后续安装、发布、真实模型调用或数据迁移。

## 7. 如何判断维护性真的提升了

不要用“文件更多”“代码更短”“测试总数更多”单独作为成功标准。建议在试点前记录基线，再用同一口径比较。

| 指标 | 本次掌握的事实 | 后续验收目标 |
| --- | --- | --- |
| 当前入口之间的状态冲突 | 已定位 INDEX 阶段说明与维护手册保存链说明的冲突 | 本次涉及的入口不再冲突；真实待验边界保留 |
| 历史数据到工作台的类型越界 | 已定位 unknown 数组与双重断言连接 | 试点连接由明确类型和解析替代，不损坏旧记录 |
| API 声明与 validator 一致性 | 已定位 generation API 局部校验较声明窄 | 每个被消费者当作可信的关键字段有检查或明确的可选语义 |
| 实现细节导致的测试修改 | 源码断言直接可见；近期审计有精确匹配修正记录 | 试点内等价重构不需要改断言字符串，破坏行为仍能被测出 |
| 模块依赖与单次变更影响范围 | 未建立全仓基线 | 先测量，不虚报下降幅度；新增依赖遵守已采纳的域边界 |
| 生命周期清理责任 | 图库/语音已有具体清理与代际实现 | 拥有者明确，迟到回调/重复清理/失败分支均有行为用例 |
| 门禁墙钟耗时与失败定位 | 本次未测量；已有执行器摘要 | 有同口径测量再决定去重，覆盖与证据可信度不降低 |
| 第三方撤回成本 | PhotoSwipe 已有默认回退与独立组件 | 业务接口不依赖查看器实现，退出或升级改动集中在适配边界 |

## 8. 验证入口与执行边界

先按当前改动使用已有工作流选取验证范围，不为纯文档调整执行全量代码门禁，也不因为已有历史通过就跳过受影响的行为回归。[S01] [S17]

```sh
# 查看现有入口；以下是可用命令说明，本审查没有执行。
npm run wf -- --help
npm run wf -- gate:quick --plan

# 文档变更：验证链接和现有文档规则。
npm run wf -- docs:check

# 前端类型/边界变更：按涉及范围选择。
npm run typecheck:app
npm run lint:js

# Node TypeScript 源码变更：生成运行文件后再运行对应 Node 测试。
npm run build:runtime
npm run typecheck:node
npm run typecheck:tests

# 跨域或构建链变更：按现有工作流选择完整范围。
npm run wf -- gate:full
```

上面不是“每项都必跑”的列表。类型/逻辑改动还须选择对应的 Vitest、Node 或契约用例；页面行为改动再加入相关浏览器回归。新增测试登记到现有清单并核对分层，不能只新增文件却没有运行入口。[S12]

办公机缺少外部参考素材时，按项目既有分工登记结构检查范围，不能将结构检查当成实物验证。对真实生成请求、TTS、Live2D、触屏、Windows 多窗口或安装产物有影响时，继续保留相应设备验收；本专题没有取得新的真实环境证据。[S02] [S03]
